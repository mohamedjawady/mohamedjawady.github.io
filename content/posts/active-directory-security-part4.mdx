> **Series Focus:** Part 3 covered turning an ACL, a delegation setting, or a certificate template into a privileged Kerberos ticket. This part covers the loop that usually surrounds that: landing on a host, stealing whatever credential material it holds, and using that material to reach the next host, repeated until something Part 3's techniques can finish the job on is within reach.

**TL;DR:** <Term concept="winrm">PowerShell Remoting</Term> is the primary lateral movement rail in most Windows environments, and its <Term concept="double-hop-problem">double-hop problem</Term> is the same delegation mechanism Part 3 covered as an escalation path, just used legitimately. Once on a host, credential material lives in specific, enumerable places: LSASS memory, the local <Term concept="sam-database">SAM database</Term>, LSA Secrets in the SECURITY hive, <Term concept="dpapi">DPAPI</Term>-protected Credential Manager and Vault entries (decryptable domain-wide via a stolen backup key), certificates, and, on hybrid-joined machines, Azure/Entra tokens including the <Term concept="primary-refresh-token">Primary Refresh Token</Term>, plus, where AD Connect or Entra Connect Sync is installed, an <Term concept="ad-connect-sync-account">on-prem sync account</Term> whose credential sits DPAPI-protected in a local database and carries DCSync-equivalent rights domain-wide. <Term concept="mimikatz">Mimikatz</Term> reads all of these, though <Term concept="credential-guard">Credential Guard</Term> blocks its classic in-memory reads on modern, properly configured hosts, which is why current tradecraft increasingly reaches for offline minidump parsing and DPAPI-specific tooling instead. <Term concept="overpass-the-hash">Over-Pass-the-Hash</Term> turns a stolen NTLM hash into a real Kerberos TGT, and everything in this post exists to eventually reach an account that can run <Term concept="dcsync">DCSync</Term>, Part 3's endgame.

## Introduction

Privilege escalation and lateral movement are not two sequential phases, they're a loop. An attacker lands on a host, steals whatever credential material that host holds, uses it to reach a second host, steals what that one holds, and repeats until something reachable is privileged enough to finish the job, usually via a Part 3 technique. This post is that loop: the rail most environments actually move over, and the specific, enumerable places Windows keeps credentials worth stealing along the way.

Same two ground rules as Part 3. Every technique is explained from what it actually does, not just named, with a diagram wherever the chain has more than two steps. And tooling gets named for what's actually current: <Term concept="mimikatz">Mimikatz</Term> is still the reference implementation for understanding these techniques, but running it unmodified against a modern, EDR-monitored, Credential Guard-enabled host is often closer to a detection test than a working attack, a point the Mimikatz section comes back to directly.

## PowerShell Remoting: The Primary Lateral Movement Rail

<Term concept="winrm">WinRM</Term>, Windows Remote Management, is the protocol behind `Enter-PSSession` and `Invoke-Command`, listening on TCP 5985 (HTTP) or 5986 (HTTPS) by default. It's the primary lateral movement rail in most Windows environments for a simple reason: it's already there, already expected in normal admin traffic, and by default only accepts a connection from an account in the target's local Administrators group, which makes a successful session a strong signal about the identity behind it, useful to both an attacker choosing where to move next and a defender triaging one.

The detail that trips up nearly everyone the first time they rely on it operationally is the <Term concept="double-hop-problem">double-hop problem</Term>. PowerShell Remoting into Server A works fine, and running commands there works fine, but the moment a command inside that session tries to reach out to a third machine, Server B, using your identity, it fails or silently falls back to an unauthenticated context. Kerberos does this on purpose: your session on Server A holds proof of who you are, but not a delegatable copy of your credential it's allowed to forward onward, precisely so that compromising Server A doesn't automatically hand over everything you have access to beyond it.

**Requirements:** membership in the target's local Administrators group (WinRM's default authorization check), or an explicit WinRM access ACE if that default has been loosened.

```bash
# from a domain-joined Windows host
Enter-PSSession -ComputerName server-a.corp.local -Credential $cred
Invoke-Command -ComputerName server-a.corp.local -ScriptBlock { whoami } -Credential $cred

# from Linux, evil-winrm is the equivalent for a captured hash or password
evil-winrm -i server-a.corp.local -u $USER -H $NTHASH
```

**Detection.** A PowerShell Remoting session spawns `wsmprovhost.exe` on the target, a reliable parent-process signal in EDR or Sysmon telemetry, especially with unusual child processes underneath it. With Script Block Logging and Module Logging enabled via Group Policy, **event 4104** captures the full text of every script executed in the session (even deobfuscated at runtime) and **event 4103** logs pipeline and module details, together the two highest-value PowerShell-specific log sources in any Windows environment. On the target, the session itself produces an ordinary **event 4624** logon.

## Credential Extraction: Where Windows Actually Keeps Secrets

Once an attacker is on a box, the question becomes what's actually extractable from it. The honest answer is: more than most people expect, spread across a small, enumerable set of well-known locations.

### LSASS: Memory

<Term concept="lsass">LSASS</Term> holds the credential material behind every currently logged-on session, and depending on what's authenticated to the box and how, that can include NTLM hashes, Kerberos tickets and their session keys, and, if a legacy provider called <Term concept="wdigest">WDigest</Term> is still enabled, a reversibly-encrypted copy of the plaintext password itself.

Mimikatz's `sekurlsa::logonpasswords` reads all of this on an unprotected host. On a host with <Term concept="credential-guard">Credential Guard</Term> enabled, that same command returns "KO - LSA Isolated": the secrets simply aren't in a memory space Mimikatz's technique can reach anymore.

**Requirements:** local Administrator (`SeDebugPrivilege`) on the target host, and no Credential Guard for the live in-memory read; offline dumping bypasses live EDR hooks on the LSASS read itself but still needs the same local admin access to create the dump.

```bash
# live, on an unprotected host
mimikatz.exe "privilege::debug" "sekurlsa::logonpasswords" "exit"

# offline: dump LSASS via a signed LOLBin, then parse away from the monitored host
rundll32.exe C:\windows\system32\comsvcs.dll, MiniDump (Get-Process lsass).Id lsass.dmp full
pypykatz lsa minidump lsass.dmp
```

**Detection:** any process opening a handle to `lsass.exe` with memory-read access is inherently worth alerting on. **Event 4656** (a handle requested to an object) with `lsass.exe` as the target, or Sysmon **event 10** (ProcessAccess) with `lsass.exe` as the target process, are the two primary native signals, and this is one of the very few places where a well-tuned allowlist (a small, known set of legitimate processes ever touch LSASS this way) makes a high-fidelity detection genuinely achievable.

### SAM and LSA Secrets: The SECURITY and SAM Hives

The <Term concept="sam-database">SAM database</Term> holds every local account's password hash on a given machine, encrypted with a machine-specific boot key. The SECURITY hive holds LSA Secrets: service account passwords stored so Windows can log them on automatically, autologon passwords if configured, and, notably for the next section, `DPAPI_SYSTEM`, the machine's own DPAPI protection secret.

```bash
# live extraction, on-host
reg.exe save hklm\sam sam.hive

```

**Detection:** reading these hives requires SYSTEM privilege or `SeBackupPrivilege`, and the classic live-extraction pattern, `reg.exe save hklm\sam`, `reg.exe save hklm\security`, `reg.exe save hklm\system` in quick succession, is specific enough to be a reliable process-creation detection on its own, alongside **event 4657** for the underlying registry value access if auditing is configured.

### DPAPI: Credential Manager, Vault, and the Domain Backup Key

<Term concept="dpapi">DPAPI</Term> is what actually protects Windows Credential Manager entries (anything saved via `cmdkey` or the Credentials applet), the Windows Vault, and some browser-saved passwords. Every DPAPI-protected secret is encrypted under a per-user master key, and that master key is where the interesting part lives: it's protected two different ways at once. One copy is derived from the user's own password (or NTLM hash), which is why an attacker who already has that can decrypt locally. The other copy is encrypted under a domain-wide public key and backed up automatically the first time the master key is created, specifically so a forgotten password doesn't mean permanently losing access to Credential Manager entries.

The domain controllers hold the private half of that backup key pair, and it never changes on its own. An attacker with Domain Admin rights extracts it once, with Mimikatz's `lsadump::backupkeys` or the equivalent in <Term concept="sharpdpapi">SharpDPAPI</Term>, and from that point on can decrypt any domain user's DPAPI-protected secrets, forever, without ever knowing that user's password.

**Requirements:** for the local-decrypt path, the target user's password or NTLM hash; for the domain-wide path, Domain Admin (or equivalent) once, to pull the backup key, after which no further privilege is needed against any individual user.

```bash
# extract the domain-wide DPAPI backup key once
mimikatz.exe "privilege::debug" "lsadump::backupkeys /system:$DC_IP /export" "exit"

# decrypt any domain user's Credential Manager / Vault blobs with it, going forward
SharpDPAPI.exe credentials /pvk:key.pvk
SharpDPAPI.exe vaults /pvk:key.pvk
```

**Detection:** the domain backup key retrieval itself is rare enough in legitimate operation to be a strong signal, DSInternals documents the specific LSA `LsaRetrievePrivateData` call pattern to alert on (`G$BCKUPKEY_PREFERRED` and `G$BCKUPKEY_P`). Individual master key or credential blob theft is harder to catch directly, which is exactly why the backup key extraction event is the control point worth instrumenting.

### Certificates

A private key marked non-exportable in the Windows certificate store is a policy setting enforced by CryptoAPI (CAPI) or CNG (the newer Cryptography API), not a cryptographic guarantee. Mimikatz's `crypto::capi` and `crypto::cng` commands patch the relevant provider in memory to strip that flag, after which the certificate exports normally. This matters directly for Part 3's AD CS content: a stolen certificate with the Client Authentication EKU authenticates via PKINIT exactly like a freshly requested one, so a certificate an attacker finds sitting on a compromised host can be just as useful as one obtained through ESC1.

**Requirements:** local Administrator on the host holding the certificate; the non-exportable flag is a user-mode policy check, so admin-level code execution is enough to patch around it.

```bash
mimikatz.exe "privilege::debug" "crypto::capi" "crypto::cng" "crypto::certificates /export" "exit"
```

### Azure and Entra Tokens

On a hybrid-joined or Entra-joined machine, the highest-value credential often isn't an AD artifact at all. A <Term concept="primary-refresh-token">Primary Refresh Token</Term> bundles proof of user sign-in with proof of device compliance, and because Conditional Access policies frequently key off device compliance, a stolen PRT doesn't just impersonate the user, it bypasses the Conditional Access policies and MFA requirements that would otherwise stop a plain stolen password cold. Tools like `ROADtoken` and `TokenTactics`, along with newer `cloudap::` functionality in Mimikatz itself, extract the PRT and MSAL token caches that browsers, Office applications, and the Azure CLI all maintain locally, turning one compromised endpoint into standing access across every cloud application tied to that identity.

**Requirements:** local Administrator (or SYSTEM) on the hybrid-joined or Entra-joined endpoint; the PRT is protected by the same TPM-backed session key the device uses, so extraction happens in-process rather than by reading a file off disk.

```bash
# extract the PRT via the Cloud AP provider, in-process
mimikatz.exe "privilege::debug" "token::elevate" "dpapi::cloudapkd /keyvalue:<...> /unprotect" "exit"

# forge a new PRT cookie for browser-based session reuse
python3 TokenTactics/PRT-Cookie-Generator.py -p $PRT -s $SESSION_KEY
```

### The AD Connect Sync Account: DCSync Rights on One Server

The PRT above is a bridge in one direction, cloud identity reaching back on-prem. Azure AD Connect (or its successor, Entra Connect Sync) builds the opposite bridge, and it does it with a standing on-prem credential most environments never think to protect the way they'd protect Domain Admin. Every AD Connect installation automatically creates an <Term concept="ad-connect-sync-account">on-prem sync account</Term>, named `MSOL_<installationID>`, and grants it the Directory Synchronization Accounts role so it can read and write the attributes sync depends on. That role carries Replicating Directory Changes rights, the same right Part 3's DCSync section is built around, across the entire on-prem domain.

The account's plaintext credential has to live somewhere the sync service can read it unattended, and that somewhere is a local SQL Server database, `ADSync.mdf`, on whichever server AD Connect is installed on, DPAPI-protected under a key that same server holds. Local Administrator on the sync server is therefore functionally equivalent to DCSync rights on the domain it syncs, a fact that turns "which server runs AD Connect" into a Tier 0 question most tiering models never ask.

**Requirements:** local Administrator (or SYSTEM) on the AD Connect / Entra Connect Sync server itself; no domain privilege of any kind is needed beforehand, since the credential the database holds is what grants it.

### Mimikatz: The Tool That Ties It Together

Every technique above has a corresponding <Term concept="mimikatz">Mimikatz</Term> module: `sekurlsa::logonpasswords` for LSASS, `lsadump::sam` and `lsadump::secrets` for the local hives, `lsadump::backupkeys` and `dpapi::masterkey`/`dpapi::cred` for DPAPI, `crypto::capi`/`crypto::cng` for certificates, and `lsadump::dcsync` for Part 3's endgame. That breadth is exactly why it's been the reference tool in this space since 2011, and exactly why its raw binary is one of the most heavily signatured pieces of software that exists: running `mimikatz.exe` unmodified on an EDR-monitored host today is closer to a live-fire detection test than a quiet operation.

Two things have shifted current tradecraft as a result. First, **Credential Guard**, now default-on for Windows 11 22H2+ and Server 2025 domain-joined non-DC systems, blocks the live in-memory reads `sekurlsa::logonpasswords` depends on, though it does not stop Kerberos ticket extraction (`sekurlsa::ekeys`) or any of the DPAPI-based techniques above, which is why operators increasingly pivot toward those instead of assuming LSASS is a dead end. Second, where LSASS access is still viable, the pattern has moved toward taking a memory dump offline (`comsvcs.dll` via `rundll32`, or a signed LOLBin equivalent) and parsing it later with a tool like `pypykatz`, entirely off the monitored host, or using a source-recompiled or BOF-based reimplementation rather than the signature-flagged public binary.

## Over-Pass-the-Hash and Pass-the-Key

Classic <Term concept="pass-the-hash">Pass the Hash</Term> reuses a captured NTLM hash directly in an NTLM authentication exchange, and it never touches Kerberos at all, which is also its weakness: NTLM is comparatively rare in a Kerberos-default AD environment, so its use stands out.

<Term concept="overpass-the-hash">Over-Pass-the-Hash</Term> does something more useful: it uses that same NTLM hash as Kerberos long-term key material to request a real TGT directly from the KDC, exactly as if the attacker had authenticated normally. The one caveat is the encryption type. Kerberos accepts RC4 keys, and an NTLM hash is valid RC4 key material as-is, so requesting a TGT with it works, but it's also an encryption-type downgrade in an AES-default environment, a detectable signal by itself. Requesting the same TGT using the account's AES key instead avoids that downgrade entirely, which is specifically why that variant gets its own name, Pass the Key.

```bash
# Over-Pass-the-Hash: RC4, produces an encryption-type downgrade
Rubeus.exe asktgt /user:$TARGET_USER /rc4:$NTHASH /domain:$DOMAIN /ptt

# Pass the Key: AES, no downgrade, blends into an AES-default environment
Rubeus.exe asktgt /user:$TARGET_USER /aes256:$AESKEY /domain:$DOMAIN /ptt
```

Both requests inject the resulting TGT directly into the current logon session. The ticket is then reusable exactly like a stolen one, <Term concept="pass-the-ticket">Pass the Ticket</Term> from that point forward.

**Detection:** an **event 4768** (TGT requested) with encryption type `0x17` (RC4) for an account in an environment that otherwise only ever uses AES is close to unambiguous, the same encryption-downgrade signal that flags Kerberoasting and AS-REP Roasting in Part 3. Pass the Key produces no such downgrade and is correspondingly harder to catch from the encryption type alone; the more durable signal there is the same identity authenticating from two hosts in a pattern inconsistent with normal usage.

## The Endgame: From Any of This to DCSync

Everything in this post is in service of one thing: reaching an account, or a hash, or a ticket, that holds Replicating Directory Changes rights, so that <Term concept="dcsync">DCSync</Term> can pull `krbtgt` and end the game with a Golden Ticket, covered in full in Part 3. It rarely takes a specific, named technique to get there; it takes whichever of the credential-extraction paths above happens to be available on whichever host is reachable next.

## Detection Recap

| Technique | Primary signal | Where to look |
|---|---|---|
| PowerShell Remoting | wsmprovhost.exe parent process; full script content | Sysmon/EDR process tree; event 4104 / 4103 |
| LSASS access | Handle opened to lsass.exe with read access | Event 4656; Sysmon event 10 |
| SAM / SECURITY hive dump | reg.exe save of SAM/SECURITY/SYSTEM in sequence | Process creation telemetry; event 4657 |
| DPAPI domain backup key theft | LsaRetrievePrivateData for G$BCKUPKEY_* | LSA API auditing (DSInternals guidance) |
| Certificate export bypass | crypto provider (CAPI/CNG) patched in-process | EDR in-memory patch detection |
| Azure/Entra token theft | PRT or MSAL cache read from an unusual process | Entra sign-in logs; device compliance anomalies |
| Over-Pass-the-Hash | AS-REQ with RC4 in an AES-default environment | Event 4768, encryption type 0x17 |
| Pass the Key / Pass the Ticket | No encryption downgrade; identity from inconsistent hosts | Behavioral/UEBA correlation, not a single event |

## Conclusion

Nothing in this post is a single dramatic exploit. It's a loop: land, extract whatever the host actually has, use it to move, repeat. PowerShell Remoting is the rail because it's already trusted. LSASS, SAM, LSA Secrets, DPAPI, certificates, and cloud tokens are the targets because Windows has to keep credential material somewhere reachable to function at all, the same tension that ran through the whole series starting with Part 1's forest and domain structure. Mimikatz's declining effectiveness against Credential Guard is a real win, but it's a win against one tool, not against the loop itself, which is exactly why every technique above got paired with a detection signal rather than left as an offense-only walkthrough. Part 3's DCSync and Golden Ticket are still where this loop ends; this post was about everything that gets an attacker there.
