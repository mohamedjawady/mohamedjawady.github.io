> **Series Focus:** Parts 3 and 4 covered getting in and moving around. This part covers staying in after the specific hole that let an attacker in gets patched, which is a different problem: persistence in Active Directory usually doesn't mean malware on a box, it means a forged credential, a patched authentication path, or a permission nobody remembered to look for.

**TL;DR:** A <Term concept="golden-ticket">Golden Ticket</Term> forged from the krbtgt hash survives until that hash is rotated twice, covered fully in Part 3. A <Term concept="silver-ticket">Silver Ticket</Term> is quieter but narrower: forged from one service account's hash, it never touches a domain controller at all. A <Term concept="diamond-ticket">Diamond Ticket</Term> starts from a real ticket and edits it, evading the detections built for tickets forged entirely from scratch. A <Term concept="sapphire-ticket">Sapphire Ticket</Term> goes one step further: instead of editing a PAC, it transplants an already-legitimate one lifted from a privileged account via S4U2Self and U2U, evading even PAC-versus-directory correlation checks, at least until a fully patched domain controller notices the transplanted PAC is missing structures only a real TGT should have. <Term concept="sid-history-injection">SID History Injection</Term> skips ticket forgery entirely: write a privileged SID into a controlled account's own `sIDHistory` attribute once, and every future legitimately-issued ticket for that account carries it forever. The <Term concept="skeleton-key">Skeleton Key</Term> patches a domain controller's LSASS in memory so every account authenticates with its real password or one attacker-chosen master password, until the DC reboots. <Term concept="dsrm">DSRM</Term> abuse turns a rarely-rotated local account on every DC into a backdoor that survives a full domain password reset. A <Term concept="custom-ssp">custom SSP</Term> sits inside LSASS logging every credential that authenticates through it, in plaintext, indefinitely. ACL-based persistence through <Term concept="adminsdholder">AdminSDHolder</Term> means a permission an admin already removed can come back on its own, every hour, until the actual backdoor is found. And <Term concept="dcshadow">DCShadow</Term> pushes any of the above through AD's own replication protocol instead of a direct write, so it never generates the LDAP-write event most of this post's detection sections rely on in the first place.

## Introduction

Getting Domain Admin once is, per Part 3, mostly a matter of finding the right misconfigured ACE, delegation setting, or certificate template. Staying Domain Admin after that specific issue gets fixed is a different skill, and it's the one most defenders think about last. Every technique in this post assumes the attacker already reached high privilege at some point and is now answering a narrower question: what survives a password reset, a patch, or an incident responder's first pass at cleanup?

Same rules as the rest of this series: every technique explained from what it actually does, a diagram wherever the mechanism isn't obvious from a sentence, and a real detection signal for each one rather than a vague "monitor for anomalies."

## Golden, Silver, Diamond, and Sapphire Tickets: Four Ways to Forge Kerberos

The <Term concept="golden-ticket">Golden Ticket</Term> is Part 3's endgame and won't be re-explained here: forge a TGT entirely offline from the krbtgt hash, valid for any username and any group membership, until krbtgt is rotated twice. What's worth adding here is the other two members of the family, because they trade the Golden Ticket's domain-wide reach for properties that matter specifically for staying hidden.

A <Term concept="silver-ticket">Silver Ticket</Term> skips the TGT step entirely. Instead of krbtgt's hash, it uses the password hash of a single service account, a SQL Server service account, a specific computer account, whatever the attacker's target actually is, and forges a TGS (service ticket) directly for that service. The forged TGS is presented straight to the target service, which decrypts it with its own key and, in most default configurations, never checks back with a domain controller to confirm the ticket is legitimate. That absence of a check is the entire point: a Golden Ticket still has to go through a KDC to get a service ticket after the TGT is minted, generating an ordinary **event 4769**, but a Silver Ticket generates neither a 4768 nor a 4769 anywhere, because the KDC was never involved at all. The cost is scope: it only works against the one service tied to the stolen hash, not the whole domain.

A <Term concept="diamond-ticket">Diamond Ticket</Term> solves a different problem: a forged-from-scratch Golden Ticket carries small tells, Mimikatz's default ten-year ticket lifetime being the most cited one, that detection tooling specifically looks for. A Diamond Ticket starts from a real TGT, requested normally through an actual AS-REQ/AS-REP exchange with a real domain controller, decrypts it offline using the krbtgt hash, edits the fields that matter (group memberships, most often), and re-encrypts it with the same krbtgt hash. Since the ticket really was issued by a DC, its lifetime, policy values, and PAC structure all look exactly like they should, because they are.

The `/ldap` and `/opsec` flags on the newer `diamond` implementation are specifically built to match real Windows AS-REQ/AS-REP behavior and pull realistic PAC values, closing the gap that made earlier diamond tickets detectable too.

Diamond Tickets still have one tell left: editing a PAC's group memberships by hand can drift from what the directory actually says about that account, and a detector correlating ticket contents against AD catches exactly that drift. A <Term concept="sapphire-ticket">Sapphire Ticket</Term> removes the hand-editing step entirely. Instead of writing a privileged group SID into a PAC, it borrows one that's already legitimate: the attacker runs an S4U2Self request as a service the attacker controls, immediately followed by a U2U (User-to-User) exchange, targeting a genuinely privileged account, which yields a real service ticket carrying that privileged account's real PAC. That PAC, exactly as issued by the KDC, is then spliced into a low-privileged user's own real TGT and re-encrypted with the krbtgt hash. Nothing in the resulting ticket was hand-edited, so there's no drift between the PAC and the directory to correlate against, only a PAC that belongs to a different account than the ticket claims to.

**Requirements:** a Silver Ticket needs only the target service account's password hash, not krbtgt, and never needs Domain Admin if that one hash is already in hand. A Diamond Ticket needs krbtgt's hash plus a valid account to request the initial real TGT from, the same prerequisite as a Golden Ticket. A Sapphire Ticket needs krbtgt's hash or AES key, control of an account with an SPN to run the S4U2Self request from, and knowledge of a genuinely privileged account to target for its PAC.

```bash
# Silver Ticket: forge a TGS directly from a service account's hash, no KDC involved
Rubeus.exe silver /service:cifs/fileserver.$DOMAIN /rc4:$SERVICE_HASH /user:anyuser /domain:$DOMAIN /sid:$DOMAIN_SID /ptt

# Diamond Ticket: starts from a real TGT, edits it, re-encrypts with krbtgt's hash
Rubeus.exe diamond /tgtdeleg /ticketuser:anyuser /ticketuserid:1234 /groups:512 /krbkey:$KRBTGT_HASH /domain:$DOMAIN /dc:$TARGET_DC /opsec /ptt

# Sapphire Ticket: Impacket's ticketer.py, transplanting a privileged account's real PAC
ticketer.py -request -impersonate administrator -domain-sid $DOMAIN_SID -domain $DOMAIN -aesKey $KRBTGT_AES_KEY -user-id 1104 lowpriv-user
```

**Detection.** Silver Tickets are the hardest of the three older variants by default, precisely because no KDC event exists to alert on; the one server-side control that catches them is setting `ValidateKdcPacSignature` to require domain controllers to validate the PAC signature on presented tickets, which a forged Silver Ticket won't have. Diamond Tickets are caught the same way Golden Tickets sometimes aren't: since the initial TGT request is completely ordinary, detection has to focus on what happens after, unexpected group membership appearing in a ticket's PAC relative to what the account actually holds in AD, which requires correlating ticket contents against the directory rather than looking for anomalies in the ticket request itself. Sapphire Tickets are built specifically to survive that correlation check, since the PAC really does belong to the privileged account it claims, which is exactly why Microsoft's October 2022 patch (KB5008380, issued alongside the fix for CVE-2021-42287) added two PAC structures, Requestor and Attributes, that only ever appear in a genuinely issued TGT: a transplanted service-ticket PAC doesn't have them, and a fully patched domain controller rejects the ticket with `KDC_ERR_TGT_REVOKED` on presentation. On a domain that hasn't applied that patch, a Sapphire Ticket has no reliable detection at all. CVE-2021-42287 itself, the PAC-lookup fallback this patch closed, is the second half of NoPac, covered in [Part 3](/posts/active-directory-security-part3).

## SID History Injection: Making Every Future Ticket Privileged, Not Just One

Every ticket-forging technique above is scoped to the ticket it forges. Forge a new one tomorrow and it's a new operation, a new opportunity to get caught. <Term concept="sid-history-injection">SID History Injection</Term> skips the forging step entirely by making the backdoor permanent at the object level: instead of writing a privileged SID into one ticket's `ExtraSids` field the way Part 6's child-to-parent escalation does, it writes that SID directly into a controlled account's own `sIDHistory` attribute. From that point on, every ticket the account gets through completely ordinary, legitimate authentication carries the injected SID in its PAC automatically, because that's exactly what `sIDHistory` is for, letting a migrated account keep access tied to a SID it no longer technically holds. No further ticket forgery, no krbtgt hash, no repeat operation: the account just is privileged now, permanently, until someone finds and removes the attribute.

The catch is getting the value in there at all. `sIDHistory` isn't writable through an ordinary LDAP modify the way most attributes are; Windows enforces that it can only be set through specific replication-aware paths, which is exactly why every practical method below either bypasses that restriction locally on a DC or calls the underlying replication primitive directly instead of going through LDAP.

**Requirements:** Domain Admin (or SYSTEM) on a domain controller for the local methods below, since the restriction that blocks a normal LDAP write to `sIDHistory` is enforced by the DC itself, not by an ACL a lower-privileged account could simply be granted around.

```bash
# pre-2016 domain controllers: Mimikatz patches the local restriction, then writes the SID
mimikatz.exe "privilege::debug" "sid::patch" "sid::add /sam:AttackerUser /new:S-1-5-21-...-512" "exit"

# 2016+ domain controllers: DSInternals edits the DIT offline (stops and restarts NTDS, ~5-10s outage)
Stop-Service NTDS -Force
Add-ADDBSidHistory -SamAccountName AttackerUser -SidHistory $DOMAIN_ADMINS_SID -DBPath C:\Windows\NTDS\ntds.dit -Force
Start-Service NTDS

# pySIDHistory, from Linux, DRSUAPI method: calls DRSAddSidHistory directly over RPC, no NTDS downtime
python3 main.py -d $DOMAIN -u $USER -p $PASSWORD --dc-ip $DC_IP --target AttackerUser --inject domain-admins --force
```

Mimikatz's `sid::patch` stopped working against Server 2016 and later, which is why DSInternals' `Add-ADDBSidHistory` became the documented fallback, at the cost of a brief authentication outage while NTDS restarts. `pySIDHistory`'s DRSUAPI method avoids that outage entirely by calling `DRSAddSidHistory` over RPC directly rather than editing the database file, though it's limited to RIDs above 1000 due to SID filtering at trust boundaries, which rules out injecting a well-known RID like Domain Admins' `-512` cross-domain but not intra-domain, where the DSInternals path remains the one that reaches any RID at all.

**Detection.** `sIDHistory` should be empty on the overwhelming majority of accounts in a single, unmigrated domain, which makes this one of the higher-signal audits available: `Get-ADUser -Filter * -Properties SIDHistory | Where-Object { $_.SIDHistory -ne $null }`, run on a schedule and compared against a documented migration record, flags anything that shouldn't be there. The write itself is visible as **event 5136** if a SACL is configured on the attribute, though the DSInternals path's NTDS service stop and restart is its own distinct, much louder tell, visible as ordinary service-control events (**event 7036**) at a time nobody scheduled maintenance.

## The Skeleton Key: One Password, Every Account

The <Term concept="skeleton-key">Skeleton Key</Term> takes a completely different approach: instead of forging tickets, it patches the authentication code path directly, in memory, on a domain controller. With Domain Admin rights and `SeDebugPrivilege`, Mimikatz's `misc::skeleton` injects into `lsass.exe` on the target DC, downgrades Kerberos encryption to RC4 for that authentication path, and installs a single master password that works alongside every account's real password, for every account in the domain, without changing anyone's actual password.

**Requirements:** Domain Admin (or equivalent) and `SeDebugPrivilege` on the target domain controller, since injecting into that DC's `lsass.exe` is the entire mechanism.

```bash
mimikatz.exe "privilege::debug" "misc::skeleton" "exit"

# from that point, any account authenticates domain-wide with its real password or:
net use \\fileserver\share /user:anyuser Mimikatz
```

## DSRM: The Backdoor Nobody Thinks of as an AD Object

Every domain controller has a <Term concept="dsrm">DSRM</Term> (Directory Services Restore Mode) local Administrator account, with a password set once at DC promotion and, in most environments, never rotated again. Normally that account only matters when the DC is booted into DSRM for database repair. The registry value `HKLM\System\CurrentControlSet\Control\Lsa\DsrmAdminLogonBehavior` controls when it can be used more broadly: `0` (default) restricts it to DSRM boot, `1` allows it if the AD DS service is stopped, and `2`, which doesn't exist by default and has to be created, allows it to authenticate over the network at any time, like an ordinary local administrator on that DC.

**Requirements:** Domain Admin (or local admin on the DC itself) to read or reset the DSRM password and to set the registry value in the first place.

```bash
# extract the DSRM local admin hash from the DC's own SAM
secretsdump.py -just-dc-user Administrator $DOMAIN/$USER:$PASSWORD@$TARGET_DC

# set the registry value that allows network logon
reg.exe add "HKLM\System\CurrentControlSet\Control\Lsa" /v DsrmAdminLogonBehavior /t REG_DWORD /d 2

# authenticate as the DSRM account, over the network, going forward
netexec smb $TARGET_DC -u Administrator -H $DSRM_HASH --local-auth
```

## Custom SSP: A Standing Wiretap Inside LSASS

## ACL-Based Persistence: AdminSDHolder and the Permission That Comes Back

Every technique so far forges or patches something. This one just grants a permission and waits, and it's arguably the hardest to fully clean up because removing it from where it's visible doesn't actually remove it.

<Term concept="adminsdholder">AdminSDHolder</Term> is a special AD object whose ACL gets copied onto every member of a set of protected groups, Domain Admins, Enterprise Admins, and similar, by a process called SDProp, which runs on the PDC Emulator (the same FSMO role from Part 1) every 60 minutes by default. It exists to stop an admin from accidentally weakening permissions on a Domain Admin account by editing it directly instead of through the group. An attacker who adds their own ACE, say `GenericAll`, to AdminSDHolder itself gets that ACE copied onto every protected account on the very next SDProp cycle, and it keeps coming back on every cycle after that, regardless of what anyone does to the protected accounts directly.

## DCShadow: Becoming a Domain Controller Just Long Enough

Every technique in this post so far leaves some kind of local trace, a forged ticket's use, a patched LSASS, a registry value, an ACE. <Term concept="dcshadow">DCShadow</Term> is different in kind: instead of writing a change and hoping it goes unaudited, it arranges for the change to never look like a write in the first place. The attacker temporarily registers their own machine as a domain controller inside AD's own replication topology, then forces a real DC to pull attacker-supplied changes from it as ordinary inbound replication, the exact mechanism real DCs use to stay in sync with each other. A change that arrives as replication doesn't pass through the same LDAP-write auditing path a normal modification does, which is precisely why this post keeps citing event 5136 as the catch for everything else: DCShadow is built specifically not to generate it.

Registering as a DC takes two pieces, both reversible: an entry under the Configuration partition's Sites container describing the attacker's machine as a server, and a change to that machine's own SPN to include the Global Catalog and DRS-replication service classes real DCs advertise. Once registered, the attacker prepares the actual change they want pushed, then forces a legitimate DC to replicate from the newly "registered" one, and unregisters immediately after. The whole cycle can complete in seconds.

**Requirements:** Domain Admin (or SYSTEM) to register the workstation and modify its own SPN, and enough local access on that same workstation to run two processes at different privilege levels, one to trigger the replication pull, one to actually speak the DRS RPC protocol as `NT-AUTHORITY\SYSTEM`.

Both require watching a layer most environments never think to instrument specifically because everything else in this post assumes the change shows up as a normal, auditable object modification, and this is the one technique built around the fact that it doesn't have to.

## Detection Recap

| Technique | Primary signal | Where to look |
|---|---|---|
| Silver Ticket | No corresponding KDC request for an accessed service | Absence of 4768/4769; ValidateKdcPacSignature enforcement |
| Diamond Ticket | PAC group membership inconsistent with AD | Correlate ticket contents against the directory, not the request itself |
| Sapphire Ticket | Transplanted PAC missing Requestor/Attributes structures | KDC_ERR_TGT_REVOKED on a DC patched per KB5008380; otherwise no reliable signal |
| SID History Injection | Non-empty sIDHistory outside a documented migration | Scheduled Get-ADUser sIDHistory audit; event 5136; event 7036 (DSInternals path) |
| Skeleton Key | Code injection / unsigned module in lsass.exe on a DC | LSASS Image File Execution Options auditing; authentication with a non-current password |
| DSRM backdoor | DsrmAdminLogonBehavior set to 1 or 2 | Registry auditing; event 4624 for the DSRM account name |
| Custom SSP | Unexpected entry in Security Packages; unsigned DLL in lsass.exe | Event 4657; Sysmon event 7 (ImageLoad) |
| AdminSDHolder ACL abuse | ACE modification on the AdminSDHolder object itself | Event 5136 with a SACL on AdminSDHolder; scheduled BloodHound ACL review |
| DCShadow | New server object under Configuration\Sites; replication from a non-DC source | No equivalent of event 5136; MDI-style monitoring of DRSReplicaAdd/DRSGetNCChanges source IPs |

## Conclusion

None of these techniques need to be re-discovered to be re-used. That's the actual defensive lesson: patching the vulnerability or misconfiguration that got an attacker in the first time does nothing to the Golden Ticket already forged, the SSP already loaded, the SID already sitting in an account's history, or the ACE already sitting on AdminSDHolder. Persistence in Active Directory is rarely a backdoor in the traditional sense, it's a credential, a patched code path, or a permission, each one durable specifically because it doesn't look like an intrusion artifact at all. Detecting them means watching the small number of places they have to leave a trace, LSASS's own integrity, a handful of specific registry values, and the ACL on one object that most defenders have never looked at directly, rather than waiting for a second, louder compromise to notice the first one never actually ended. DCShadow is the exception worth remembering last: it exists specifically to avoid leaving even those traces, which is why it's the one technique in this post that gets caught upstream, at the network layer, or not at all.
