> **Series Focus:** Part 1 stated it plainly: a Domain Admin in one domain is not automatically an admin anywhere else in the forest, but an Enterprise Admin or a compromised Schema Master is, "which is the detail that makes 'just isolate the child domain' a much weaker mitigation than it sounds." This part is that detail, worked all the way through: what actually lets authentication cross a trust, and the two distinct ways a compromised side of one turns into control of the other.

**TL;DR:** Every trust, inside a forest or between two forests, is backed by a shared secret, the <Term concept="inter-realm-trust-key">inter-realm trust key</Term>, that lets one side's domain controller vouch for a user crossing into the other side. A child domain's krbtgt hash forges a Golden Ticket valid only in that child domain, until <Term concept="sid-history">SID History</Term> is added to it: writing the parent's Enterprise Admins SID into the ticket's ExtraSids field escalates a single child domain compromise to full forest control, and it works specifically because <Term concept="sid-filtering">SID filtering</Term>, the control meant to stop exactly this, is off by default on intra-forest trusts. Stealing the trust key itself is the second path, and it works the same way across an actual forest or external trust, where SID filtering is on by default and has to be found already weakened, or a real business reason for having weakened it, before it goes anywhere.

## Introduction

Everything in Parts 3 through 5 stayed inside one domain. This post is about the boundary above it: what a trust relationship actually is under the hood, and the two distinct ways compromising one side of it escalates into the other. Both techniques below ultimately touch the same mechanism, the shared key that makes cross-domain authentication possible at all, but they reach it from different starting points and are stopped, or not, by the same single setting.

## How a Trust Actually Authenticates Across the Boundary

A trust is not a policy statement, it's a shared secret. When two domains (or two forests) establish a trust, each side creates a Trusted Domain Object holding, among other things, an <Term concept="inter-realm-trust-key">inter-realm trust key</Term>, effectively a password, identical on both sides. When a user in Domain A requests access to a resource in Domain B, Domain A's KDC can't issue a normal service ticket for a domain it doesn't control, so instead it issues a referral: an inter-realm TGT encrypted with the shared trust key rather than krbtgt. The user presents that referral to a DC in Domain B, which decrypts it with its own copy of the same trust key, confirms it's legitimate, and issues an ordinary service ticket from there.

## Child-to-Parent: Golden Ticket with SID History

A Golden Ticket forged from a child domain's krbtgt hash, Part 3's endgame, is valid for any username and any group membership, but only inside that child domain, since it's krbtgt-signed, not trust-key-signed. Getting it to reach the parent domain, or the whole forest, needs one more piece: <Term concept="sid-history">SID History</Term>.

SID History exists for a legitimate reason: when a user is migrated from one domain to another, tools like ADMT copy their old SID into the new account's SID History attribute so access permissioned against the old SID keeps working during the transition. Kerberos writes every SID in that attribute into the ticket's PAC alongside the account's own SID, which means anything holding those SIDs is granted, not just the account itself. Rubeus's `/sids` flag (or Mimikatz's `kerberos::golden /sids`) writes an arbitrary SID directly into a forged ticket's PAC the same way, and the SID an attacker actually wants there is the parent domain's Enterprise Admins group.

**Requirements:** the child domain's krbtgt hash (via DCSync, Part 3's endgame, scoped to the child) and the parent domain's Enterprise Admins group SID, which is just the parent's domain SID with the well-known `-519` RID appended.

```bash
# pull the child domain's krbtgt hash
secretsdump.py -just-dc-user krbtgt $CHILD_DOMAIN/$USER:$PASSWORD@$CHILD_DC

# forge a Golden Ticket in the child domain, with the parent's Enterprise Admins SID added
Rubeus.exe golden /rc4:$CHILD_KRBTGT_HASH /domain:$CHILD_DOMAIN /sid:$CHILD_DOMAIN_SID /sids:$PARENT_DOMAIN_SID-519 /user:anyuser /ptt

# equivalent with Mimikatz
kerberos::golden /user:anyuser /domain:$CHILD_DOMAIN /sid:$CHILD_DOMAIN_SID /krbtgt:$CHILD_KRBTGT_HASH /sids:$PARENT_DOMAIN_SID-519 /ptt
```

## Crossing a Trust Directly: Stolen Trust Keys and Forged Inter-Realm Tickets

The second path doesn't need a child domain relationship at all, any bidirectional trust will do, forest or external. An attacker with Domain Admin rights on one side of the trust extracts the inter-realm trust key itself, with Mimikatz's `lsadump::trust /patch` on a domain controller or by DCSyncing the Trusted Domain Object directly, and then forges an inter-realm TGT signed with that stolen key, the same referral mechanism the legitimate exchange above uses, claiming whatever group membership the attacker wants via the same ExtraSids mechanism.

**Requirements:** Domain Admin (or equivalent) on one side of any bidirectional trust, plus, for the privileged-SID claim to actually land, SID filtering already relaxed on that trust, since it's on by default for forest and external trusts.

```bash
# extract the inter-realm trust key from a domain controller
mimikatz.exe "privilege::debug" "lsadump::trust /patch" "exit"

# or DCSync the Trusted Domain Object directly
secretsdump.py -just-dc $DOMAIN/$USER:$PASSWORD@$DC_IP

# forge an inter-realm TGT signed with the stolen key, claiming a privileged SID
Rubeus.exe golden /rc4:$TRUST_KEY /domain:$DOMAIN /sid:$DOMAIN_SID /sids:$TARGET_DOMAIN_SID-519 /user:anyuser /ticket:trust_tkt.kirbi
Rubeus.exe asktgs /ticket:trust_tkt.kirbi /service:cifs/target.$TRUSTED_DOMAIN /dc:$TRUSTED_DC /ptt
```

## SID Filtering: The Inconsistent Default That Decides Which of These Work

Both techniques above ultimately depend on the same setting, and its default value is not consistent across trust types, which is exactly why Part 1 called domain isolation a weaker mitigation than it sounds.

| Trust type | SID filtering (quarantine) default | Practical effect |
|---|---|---|
| Parent-child (intra-forest) | Off | ExtraSids from a child domain are honored in the parent without restriction |
| Tree-root (intra-forest) | Off | Same as parent-child: every domain in a forest is treated as equally trusted |
| Forest trust | On | Foreign SIDs are stripped unless filtering has been explicitly relaxed |
| External trust | On | Same as forest trusts: the more common target for `netdom /enablesidhistory:yes` left on after a migration |

Microsoft's own reasoning for the intra-forest default is that every domain in a single forest is already administratively unified, so filtering between them is redundant, the same logic behind Part 1's claim that the forest is the real boundary. The practical consequence is that a single child domain, often the one judged least critical and secured accordingly, is a direct path to full forest compromise, not a contained blast radius.

**Detection.** Trust key extraction (`lsadump::trust` or a DCSync scoped to a Trusted Domain Object) is detectable the same way ordinary DCSync is, covered in Part 3: **event 4662** for a replication-style request against the TDO from a source that isn't a domain controller. SID History abuse is best caught at the object level: any account with a non-empty `sIDHistory` attribute that wasn't the result of a documented, tracked migration is worth alerting on outright, since legitimate uses of the attribute are rare and time-bound while forged uses are neither. Tools built for exactly this, like Microsoft's `Get-ADUser -Filter 'sIDHistory -like "*"'` scoped across the forest, or a scheduled BloodHound collection that flags foreign-domain SIDs, turn an otherwise invisible ticket-level abuse into a standing object-level audit.

## Conclusion

Part 1 spent one sentence on this: an Enterprise Admin, or a compromised Schema Master, is privileged everywhere in the forest, which makes isolating a child domain weaker than it sounds. This post was that sentence, worked all the way through. Both paths here, SID History riding an intra-forest trust with its filter off by default, and a stolen trust key riding a forest or external trust with its filter on but sometimes quietly relaxed, end at the same place: a security boundary that most organizations draw at the domain, when Active Directory itself draws it at the forest. Treating a child domain, or a trusted external forest, as a separate security posture rather than an equally privileged part of the same one is the assumption every technique in this post depends on someone else having made.
