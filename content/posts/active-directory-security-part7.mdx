> **Series Focus:** Every detection recap table from Parts 3 through 6 leaned on domain controller event logs and Microsoft Defender for Identity, the identity half of the stack. This part is the other half: what actually runs on the endpoint an attacker is standing on, how Attack Surface Reduction rules intercept specific technique behaviors before an alert even fires, and a single table rolling up everything this series has covered by which layer catches it.

**TL;DR:** <Term concept="mde">Microsoft Defender for Endpoint</Term> and <Term concept="asr-rules">Attack Surface Reduction rules</Term> are the endpoint-side complement to the DC-log and Defender for Identity signals covered throughout this series, intercepting behaviors like LSASS memory access and PSExec/WMI-spawned processes by exact rule GUID rather than by signature. <Term concept="lsa-protection">LSA Protection</Term> and Credential Guard, covered in Part 4, make the LSASS ASR rule redundant where both are already enabled, worth knowing before deploying overlapping controls. Most of the tools named across this series, Rubeus, Mimikatz, Certipy, NetExec, leave process-creation and command-line patterns specific enough to alert on directly. None of this replaces the DC-log and MDI signals from Parts 3 through 6, it closes the gap they can't see: what happens on the box before any of that traffic ever reaches a domain controller.

## Introduction

Every technique in this series has a detection recap table, and every one of those tables is honest about where its strength lies: domain controller event logs and Microsoft Defender for Identity, which watches Kerberos and LDAP traffic directly. That's the identity layer, and it's necessary but not sufficient, because by the time a forged ticket or a DCSync request reaches a domain controller, the credential material behind it was very likely already extracted somewhere else, on an endpoint, using LSASS, a registry hive, or a DPAPI blob, exactly as covered in Part 4. This post is that other layer: what an EDR agent actually sees before any of that traffic exists, using Microsoft Defender for Endpoint and Attack Surface Reduction rules as the concrete example, since they're free with every licensed Windows endpoint and directly cover a meaningful slice of this series' techniques.

## What an EDR Actually Sees

An EDR agent doesn't read minds, it reads a specific set of Windows APIs: process creation, handle requests to sensitive processes like `lsass.exe`, DLL and driver loads, and, through the Antimalware Scan Interface (AMSI), the deobfuscated content of scripts right before they execute. Everything downstream, correlation, alerting, blocking, is built on those raw signals, which is why the process-level detections in this post and the DC-log detections from earlier parts genuinely see different things: an EDR agent has no visibility into a Kerberos ticket's contents, and a domain controller has no visibility into what process just opened a handle to LSASS on a workstation three network hops away.

## Attack Surface Reduction: Blocking Behavior, Not Signatures

<Term concept="asr-rules">ASR rules</Term> are a Microsoft Defender Antivirus feature, available even outside a full MDE deployment, that block or audit specific behaviors by rule GUID rather than by matching a known-bad file. Three of the eighteen standard rules map directly onto techniques covered earlier in this series.

| ASR rule | GUID | What it stops |
|---|---|---|
| Block credential stealing from the Windows local security authority subsystem | `9e6c4e1f-7d60-472f-ba1a-a39ef669e4b2` | Untrusted processes opening LSASS with memory-read access, the exact behavior Part 4's `sekurlsa::logonpasswords` depends on |
| Block process creations originating from PSExec and WMI commands | `d1e49aac-8f56-4280-b9ba-993a6d77406c` | Child processes spawned via PsExec or WMI, common lateral movement rails alongside Part 4's PowerShell Remoting |
| Block persistence through WMI event subscription | `e6db77e5-3df2-4cf1-b95a-636979351e5b` | WMI-based persistence, the closest ASR equivalent to Part 5's registry- and LSASS-based persistence mechanisms |
| Block execution of potentially obfuscated scripts | `5beb7efe-fd9a-4556-801d-275e5ffc04cc` | Obfuscated PowerShell, relevant wherever this series' tooling gets wrapped for delivery |

The LSASS rule is worth a specific technical note, because how it works matters for what it actually stops: it doesn't block a process from running, it blocks that process's attempt to open LSASS with memory-read access, and lets the process continue otherwise. A tool with Mimikatz's LSASS-reading behavior still launches successfully; it just gets nothing when it reaches for LSASS.

Every rule writes to the Windows Defender Operational log: **event 1121** for a block, **event 1122** for an audit hit (the rule would have blocked, had it been in Block mode rather than Audit). Deploying in Audit first and reviewing 1122 volume for a few weeks before flipping to Block is Microsoft's own recommended rollout, since the LSASS rule specifically generates high audit volume from entirely benign processes that enumerate LSASS without reading anything sensitive from it.

One overlap worth knowing before turning all of this on at once: <Term concept="lsa-protection">LSA Protection</Term> (RunAsPPL), which runs LSASS as a kernel-protected process, and Part 4's Credential Guard both already restrict LSASS access at a lower level than an ASR rule can. Per Microsoft's own guidance, the LSASS ASR rule provides no additional protection where both are already enabled, and is classified as not applicable in Defender for Endpoint's own management settings in that configuration. Layering it on anyway isn't harmful, but it isn't buying anything either.

## Process-Level Signals for This Series' Tooling

Most of the tools named throughout Parts 3 through 6 leave a specific enough process-creation or command-line footprint to alert on directly, independent of whatever ASR rules or AV signatures are or aren't in place.

| Tool / pattern | What to look for |
|---|---|
| Rubeus | Command-line arguments like `kerberoast`, `asreproast`, `s4u`, `golden`, `silver`, `diamond`, `ptt`; these survive binary renaming since they're arguments, not the file itself |
| Mimikatz | Command patterns like `sekurlsa::`, `lsadump::`, `kerberos::golden`; more durably, any unexpected process opening a read handle to `lsass.exe` |
| rundll32 LSASS dump | `rundll32.exe` spawning with `comsvcs.dll` and the MiniDump export (ordinal 24) as arguments, the offline-dump technique Part 4 mentioned as a Credential Guard workaround |
| Certipy | Certificate requests against AD CS web enrollment or RPC endpoints from hosts that aren't part of normal PKI administration |
| NetExec | LDAP or SMB enumeration bursts, especially command lines carrying `--kerberoasting` or `--asreproast` |
| targetedKerberoast.py | A `servicePrincipalName` attribute written and deleted within seconds, covered in Part 3 as event 5136, but worth flagging here as a process-adjacent artifact too |
| wsmprovhost.exe | Appearing as the parent of `cmd.exe` or `powershell.exe` on a server that isn't a normal PowerShell Remoting target |

None of these individually prove compromise. All of them are cheap to write as detection rules and expensive for an attacker to avoid entirely, since renaming a binary doesn't change its command-line grammar or its behavior toward LSASS.

## Conclusion

This series started with what Active Directory actually is, walked through how it gets mapped, escalated, moved through, persisted in, and finally how a trust extends all of that beyond one domain entirely. This post is the closing argument for why none of those earlier detection tables were ever meant to stand alone: an identity-layer signal like a 4769 burst or an MDI DCSync alert tells you something crossed a domain controller, and an endpoint-layer signal like an ASR block or a Sysmon LSASS access tells you something happened on a box before it ever got that far. Neither one replaces the other, and an attacker who only has to evade one of them still has to get past the rest. That's the actual argument for defense in depth in an AD environment: not that more tools are better in the abstract, but that this series' techniques, every one of them, cross at least one of these layers on the way to working at all.
