> **Series Focus:** A modern SOC doesn't watch a network edge anymore, because for most organizations that edge stopped being where the attacks happen. This series walks the workflow of a mature cloud-first SOC in order: this part covers the architecture being defended, Part 2 covers how detections get built against it, Part 3 covers investigating an incident across it, and Part 4 covers hunting through it before an alert ever fires.

**TL;DR:** The security perimeter used to be a physical boundary, a firewall between "inside" and "outside" that VPNs punched a controlled hole through. That model assumed users, devices, and applications all lived inside the boundary most of the time, an assumption that remote work and SaaS adoption broke completely. What replaced it isn't a new wall, it's a set of five layers, identity, device trust, network edge, SaaS, and cloud infrastructure, each independently verifying every request instead of trusting anything by virtue of location. This post maps that architecture layer by layer, with the named products that typically occupy each one, so the next three posts in this series have a concrete environment to build detections, investigations, and hunts against.

## Introduction

If you ask a SOC analyst from 2012 to draw the network they were defending, you'd get a fairly consistent picture: a corporate LAN, a DMZ, a firewall, and a VPN concentrator for the small fraction of users working remotely. Everything that mattered lived inside a boundary you could point to on a diagram, and the entire security model was organized around defending that boundary and watching what crossed it.

Ask the same question of an analyst defending a SaaS-first company today and the diagram falls apart. There is no LAN in the old sense, employees work from home networks, coffee shops, and airports as the default rather than the exception. The applications they use, email, file storage, CRM, code repositories, mostly aren't hosted on anything the company owns; they're SaaS platforms reached directly over the internet. The servers that do exist are virtual machines and managed services running in someone else's data center. None of this is a hypothetical future state, it's the default architecture for most organizations founded in the last decade and the destination most older organizations are migrating toward.

This post is about what replaced the old perimeter, not as an abstract trend but as a concrete set of layers with real products sitting in each one, because Part 2 through Part 4 of this series build directly on this map: you can't design a detection, run an investigation, or hunt effectively through an architecture you haven't first understood.

## The Evolution: On-Premises, Hybrid, Cloud-Native

Three architectural eras coexist across the industry right now, and most SOCs are defending some mix of all three rather than a clean transition from one to the next.

**On-premises** is the model the industry built its security tooling around for two decades: a physical network boundary, Active Directory as the identity source, a SIEM ingesting firewall and Windows event logs, and a security team that could reasonably assume "on the corporate network" and "trusted" were close enough to the same thing. <Term concept="active-directory">Active Directory</Term>, covered in depth elsewhere on this blog, is still the identity backbone for a large share of the enterprise world, and a lot of what a SOC does in this model is genuinely still relevant.

**Hybrid** is where most established organizations actually sit: on-prem AD synchronized to a cloud identity provider (Entra ID via Entra Connect being the most common pairing), some workloads still in a data center, others migrated to AWS, Azure, or GCP, and a growing share of day-to-day work happening in SaaS applications the security team doesn't run infrastructure for at all. This is architecturally the hardest era to defend well, because it inherits the attack surface of both models simultaneously without fully getting the tooling maturity of either.

**Cloud-native** is the model this series focuses on: no on-premises Active Directory, no traditional network perimeter, identity provided entirely by a cloud IdP, infrastructure entirely in one or more cloud providers, and a workforce that authenticates to individual applications directly over the internet rather than tunneling into a private network first. This is the fastest-growing category and the one existing SOC playbooks, largely written for the on-premises era, cover the least.

## Why the Perimeter Disappeared

Two forces did this, and they compounded each other.

**Remote work** removed the assumption that most users, most of the time, were physically inside a network boundary. A VPN can extend that boundary to a remote user, but it does so by giving a remote laptop the same network-level trust a machine on the office LAN would have had, which is a worse security property than it sounds: a compromised remote laptop with an active VPN tunnel has the same lateral movement options a compromised office machine would.

**SaaS adoption** removed the assumption that the applications users need live inside that boundary at all. When email, file storage, and core business applications are all reached directly over the public internet, "the network perimeter" stops being the place where most access decisions actually get made. The access decision moved to the identity layer, whether or not the security architecture moved with it.

## Zero Trust: The Principle Behind the Architecture

<Term concept="zero-trust">Zero Trust</Term> is often described as a product category, and vendors are happy to let that confusion persist, but it's a principle: never trust a request by default, verify it explicitly every time, regardless of where it originates, and grant the least access necessary for that specific request. In practice this means a request from a laptop already sitting on the corporate network gets exactly as much scrutiny as one from a coffee shop, because network location stopped being a meaningful trust signal once both are equally reachable over the internet and equally capable of being a compromised device.

The practical consequence for architecture is that trust now gets established independently at each of the five layers below, rather than once at a network boundary and implicitly extended everywhere after. That independence is precisely what makes cross-layer correlation, the subject of Parts 2 through 4, both necessary and difficult: an attacker who clears one layer's check hasn't cleared the rest, but a SOC that only monitors one layer can't tell the difference between "cleared all five" and "cleared the one we're watching."

Concretely: a Fintrail engineer opening the AWS console from their desk on the corporate WiFi and the same engineer opening it from an airport lounge go through the identical sequence of checks. Identity confirms the sign-in and evaluates Conditional Access risk. Device trust confirms the laptop is enrolled and compliant. The ZTNA layer confirms the specific console application was authorized for this identity, on this device, right now, not at some point in the past. None of those three checks reference "is this the office network," because under Zero Trust that fact was never actually part of the trust decision, it just used to be a reasonable proxy for it. The office WiFi sign-in isn't trusted more, it's checked exactly as thoroughly, and that's the entire point: the old model gave the office sign-in a pass the airport one didn't get, and that pass is precisely what a compromised office machine or an insider would have exploited.

### Identity

Identity is the layer every other layer now defers to. **Microsoft Entra ID** (formerly Azure AD) and **Google Workspace** are the two identity providers most cloud-first organizations build around, with **Okta** common as a dedicated IdP layered in front of both when an organization needs a single identity plane across a mixed SaaS estate. This layer owns authentication, <Term concept="mfa">multi-factor authentication</Term> enforcement, and <Term concept="conditional-access">Conditional Access</Term> policies, the rules that decide whether a specific sign-in, from a specific device, in a specific location, gets allowed, challenged, or blocked. It's also the layer that generates the sign-in and audit logs Part 2 builds detections against.

### Device Trust

A verified identity on an unmanaged, unpatched, or already-compromised device is not actually a trustworthy request, which is why device posture, managed via **Microsoft Intune** or **Jamf** for macOS, feeds into the access decisions made at the identity and network-edge layers rather than standing alone. A Conditional Access policy that says "require MFA" and one that says "require MFA and a compliant, managed device" are very different security postures, and the difference is exactly this layer.

### Network Edge / ZTNA

This is where the VPN used to sit, and where <Term concept="ztna">ZTNA</Term> (Zero Trust Network Access) now sits instead. **Zscaler Private Access (ZPA)** and **Cloudflare Access** are two representative examples of this category: both replace "connect to the corporate network, then reach internal resources" with "authenticate per application, per request, with no broad network-level tunnel granted at all." The practical security difference from a VPN is significant: a compromised ZTNA session can reach the one application it was authorized for, not every host reachable on a flat internal network. **Cloudflare WAF** sits at the same conceptual layer for public-facing web applications specifically, filtering requests before they reach the application (the same WAF role covered from the application-security side in this blog's Visibility for Defenders post).

### SaaS

The application layer itself, email, file storage and collaboration (Google Workspace, Microsoft 365), CRM, code hosting, and the dozens of smaller SaaS tools a typical org accumulates. Each of these is its own control plane with its own admin roles, its own audit log format, and its own OAuth grant mechanism, which is exactly the fragmentation this blog's Visibility for Defenders post covered under Cloud/SaaS collection and CASB/SSPM tooling.

### Cloud Infrastructure

**AWS**, **Azure**, and **GCP** host the compute, storage, and managed services an organization actually runs, as opposed to consumes as SaaS. IAM policies, security groups, and each provider's own audit trail (**AWS CloudTrail** being the canonical example, referenced again in Part 2) live here. This is also where the modern attack surface below gets most concrete: a misconfigured storage bucket or an over-permissioned IAM role is a cloud-infrastructure-layer problem with consequences that can cross every other layer above it.

## The Modern Attack Surface

Mapping the five layers onto attack surface makes the shift concrete: an attacker no longer needs to breach a network boundary at all. A phished credential against Entra ID or Google Workspace, an OAuth grant approved by a tricked user, or a leaked AWS access key are all complete initial-access vectors that never touch anything resembling the old perimeter. Part 3 of this series walks exactly this kind of chain, phishing straight through identity, ZTNA, and cloud console access to data exfiltration, step by step.

| Initial-access vector | Layer it lands in | Why the old perimeter never saw it |
|---|---|---|
| Phished credential (password + MFA via an <Term concept="aitm">AiTM</Term> kit) | Identity | The request goes directly to the identity provider over the public internet; no network boundary is ever crossed |
| OAuth consent grant approved by a tricked user | SaaS | Application-to-application authorization, entirely inside the SaaS platform's own API surface |
| Leaked or committed cloud access key | Cloud infrastructure | Usable from anywhere against the provider's API; the key itself is the only credential that matters |
| Compromised personal or unmanaged device reaching SaaS directly | Device trust / SaaS | No corporate network involved at any point in the session |
| Misconfigured, publicly exposed storage bucket or API | Cloud infrastructure | Public by configuration from the start; there was never a perimeter to breach |

This is also why endpoint visibility hasn't become less important, it's become one layer among five rather than the primary one. **Windows and macOS endpoints**, monitored by whatever EDR platform an org runs (this blog's Visibility for Defenders post names several), still matter enormously, they're just no longer the only place an attack chain can be observed, and in a cloud-native org, often not even the first place.

| Device Trust | Microsoft Intune, Jamf | Device enrollment, compliance/posture checks feeding access decisions |

| SaaS | Google Workspace, Microsoft 365, and the broader SaaS estate | The applications themselves, each with its own admin roles and audit logs |
| Cloud Infrastructure | AWS, Azure, GCP | Compute, storage, managed services, IAM, and platform audit trails (CloudTrail and equivalents) |
