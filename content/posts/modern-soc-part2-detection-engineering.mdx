> **Series Focus:** [Part 1](/posts/modern-soc-part1-architecture) mapped the five-layer architecture a modern SOC defends: identity, device trust, network edge, SaaS, and cloud infrastructure. This part is about turning the telemetry each of those layers produces into detection logic that actually catches something, and doesn't catch everything else along with it.

**TL;DR:** Detection engineering is the discipline of converting a specific, testable claim about attacker behavior into logic that fires reliably on that behavior and rarely on anything else. It starts from telemetry, <Term concept="mitre-att-ck">MITRE ATT&CK</Term>-mapped threat modeling decides what's worth building a detection for, and it ends in a tuned, correlated rule with a documented false-positive rate, not a one-off query someone wrote during an incident and never touched again. This post covers the lifecycle, the telemetry sources a cloud-native org actually has (CloudTrail, Google Workspace audit logs, Cloudflare WAF logs, DNS, auth logs, EDR events), eight concrete detection examples, and a lab that has you write real Sigma rules and explain the logic behind each one.

## Introduction

An alert and a detection are not the same thing, and conflating them is where a lot of SOC maturity problems start. A detection is engineered: it starts from a specific behavior worth catching, gets built against real telemetry, gets tested against both attack and benign traffic, and gets tuned over time based on what it actually produces in production. An alert is just whatever came out the other end, useful or not. A SOC that treats every alert as if it were a validated detection ends up with an inbox full of noise and, eventually, an analyst corps that stops trusting any of it, which is the exact failure mode that let real intrusions sit unnoticed next to a thousand ignored false positives.

This post is about doing detection engineering properly against the architecture Part 1 described: not "what does our SIEM support," but "given that identity, device trust, network edge, SaaS, and cloud infrastructure are five separate control planes, what does a detection need to look like to catch behavior that crosses between them."

**Threat modeling** decides what's worth a detection at all, ideally anchored to <Term concept="mitre-att-ck">MITRE ATT&CK</Term> so the choice is traceable to real adversary behavior rather than whatever seemed interesting that week. **Telemetry mapping** asks, for the chosen technique, which of the five architectural layers would actually produce a signal, the same discipline this blog's Visibility for Defenders post applies as a coverage map. **Rule development** is where the actual logic gets written. **Testing** against both real attack data (or a credible simulation of it) and a representative sample of benign traffic is the step most skipped under time pressure, and the one whose absence explains most bad detections in production. **Deploy and tune** covers correlation and risk-based alerting, both covered below. **Measurement** closes the loop: a detection without a tracked false-positive rate and a tracked true-positive count isn't actually being managed, it's just running.

### Detection vs. Alert, and Why False Positives Aren't a Rounding Error

A **detection** is the engineered logic. An **alert** is one instance of that logic firing. The distinction matters because a detection can be well-engineered and still generate mostly false positives if it's watching for something that's also common in legitimate use, impossible travel being the clearest example below: the logic is simple and correct, and it still needs tuning against how your specific organization's travel patterns actually look, or it drowns real signal in noise from VPN exit-node hopping and airline WiFi.

<Term concept="correlation">Correlation</Term> and <Term concept="risk-based-alerting">risk-based alerting</Term> are the two main levers for taming that noise without just turning the detection off. Correlation raises confidence by requiring multiple, independently weak signals to co-occur (a new-country sign-in alone is weak, a new-country sign-in immediately followed by an MFA registration change is not). Risk-based alerting scores each signal instead of treating every rule as a binary fire/don't-fire, so a SOC can triage a stack of moderate-confidence signals on one identity as a single elevated-priority case instead of ten separate low-priority tickets nobody has time for.

A concrete version of that scoring, applied to one identity in one session, might look like: new country for this user, +20; sign-in from an ASN never seen before for this user, +25; MFA satisfied via push rather than a phishing-resistant method, +10; new OAuth grant within the same session, +30. Any single one of those signals sits well below a reasonable alert threshold (say, 60) on its own, a user really can travel, really can get a new ISP, really can approve a legitimate app. All four together in one session clear the threshold easily, and that's the case that should page someone, not any individual signal in isolation. The specific weights matter far less than the principle: they should come from tuning against your own environment's actual false-positive history, not from a vendor's default configuration left untouched.

## Telemetry Sources

The detections below are only as good as what's actually being collected, which is the same caveat the Visibility for Defenders post makes at the collection-point level, applied here specifically to a cloud-native stack.

| Source | Layer (from Part 1) | What it captures | Example event fields |
|---|---|---|---|
| AWS CloudTrail (and Azure Activity Log / GCP Audit Logs) | Cloud infrastructure | Every API call against the cloud control plane: who, what action, what resource, from where | `eventName`, `sourceIPAddress`, `userIdentity`, `requestParameters` |
| Google Workspace audit logs | SaaS / Identity | Admin actions, OAuth grants, sign-ins, sharing changes across the Workspace suite | `events.name`, `actor.email`, `ipAddress`, `parameters` |
| Cloudflare WAF logs | Network edge | Request-level matches against WAF rules for public-facing applications | `Action`, `RuleID`, `ClientIP`, `ClientRequestURI` |
| DNS logs | Network edge | Every resolution request, useful for both C2 detection and shadow-IT discovery | `query_name`, `query_type`, `response`, `client_ip` |
| Identity / authentication logs | Identity | Sign-ins, MFA challenges and results, Conditional Access decisions | `status`, `location`, `deviceDetail`, `conditionalAccessStatus` |
| EDR events | Endpoint | Process creation, network connections, and behavioral flags from the host itself | `process_name`, `command_line`, `parent_process`, `hash` |

## Eight Detection Examples

Each of these follows the same shape: what the behavior actually is, which telemetry source(s) it needs, and where it tends to produce false positives if the logic is too naive.

**1. Impossible travel.** Two sign-ins from the same identity, from geographically distant locations, in a window of time shorter than physical travel would allow. Needs identity sign-in logs with geolocation. False-positive risk is significant: VPN exit nodes, corporate proxies, and legitimately fast travel all trigger naive versions of this rule, which is why most mature implementations correlate it with a change in device fingerprint or a new, never-seen-before ASN rather than firing on geolocation delta alone.

**2. OAuth abuse.** A user approves a malicious or over-scoped third-party application's OAuth consent request, the exact mechanism behind Scenario 3 in this blog's Visibility for Defenders post. Needs Google Workspace or Microsoft 365 OAuth grant audit events. Detection logic typically flags grants requesting high-risk scopes (mail read, full drive access) to applications outside an approved publisher allowlist.

**3. MFA fatigue.** A high volume of MFA push notifications sent to one user in a short window, the pattern behind several well-documented real-world breaches where a user eventually approved a prompt just to make it stop. Needs identity authentication logs with per-challenge granularity. Detection logic counts distinct MFA denials or repeated prompts to the same user within a short window, not just the eventual approval.

**4. Suspicious AssumeRole.** An AWS <Term concept="assume-role">AssumeRole</Term> call from an unusual source (a principal or IP that has never assumed that role before, or an assumption immediately followed by unusually broad API activity). Needs CloudTrail. This is the cloud-infrastructure-layer equivalent of lateral movement, and one of the clearest illustrations of why identity telemetry alone doesn't cover a cloud-native environment, the interesting behavior happens entirely inside the cloud provider's own control plane.

**5. New administrator creation.** A new user is granted an administrative role in Google Workspace, Microsoft 365, or a cloud provider's IAM. Needs the relevant platform's admin audit log. Low false-positive rate by design (admin creation should be rare and always intentional), which makes it a good candidate for a low-threshold, high-priority alert rather than a correlated one.

**6. Impossible API activity.** A service account or programmatic identity suddenly calling APIs it has never called before, or at a volume far outside its historical baseline. Needs CloudTrail or equivalent plus a behavioral baseline (see NDR's baselining approach, covered in the Visibility for Defenders tools table, for the same underlying idea applied to network traffic instead of API calls).

**7. Credential stuffing.** A burst of failed authentication attempts against many different usernames from the same source, or the same username from many different sources, distinguishable from ordinary brute-forcing by its scale and its use of previously breached credential lists. Needs identity authentication logs, ideally with a threat-intel feed cross-reference against known-breached credentials.

**8. Cloud resource discovery.** A principal enumerating IAM roles, S3 buckets, or EC2 instances in a pattern consistent with `aws iam list-*` / `s3 ls` reconnaissance rather than normal operational activity, often the first thing an attacker with a stolen cloud credential does. Needs CloudTrail. ## Lab: Write Sigma Rules for Three of the Detections Above

<CollapsibleCode title="Sigma Rules: Suspicious AssumeRole, MFA Fatigue, New Admin Creation" language="yaml">

```yaml
title: Suspicious AssumeRole Followed by Rapid Enumeration
id: 8f2a1c3e-0000-4000-8000-000000000001
status: experimental
description: >
  Detects an IAM principal assuming a role it has not assumed in the prior
  30 days, followed within 5 minutes by a burst of read-only list/describe
  API calls, consistent with post-compromise cloud reconnaissance.
logsource:
  product: aws
  service: cloudtrail
detection:
  assume_role:
    eventName: AssumeRole
  enumeration:
    eventName|startswith:
      - 'List'
      - 'Describe'
  timeframe: 5m
  condition: assume_role followed by enumeration | count(enumeration) by requestParameters.roleArn > 10
falsepositives:
  - Legitimate automation/CI roles performing routine inventory scans
  - New engineers assuming a role for the first time as part of onboarding
level: high
# Reasoning: neither event alone is a reliable signal (engineers assume
# roles and list resources constantly). The rule requires BOTH a
# first-time-in-30-days assumption AND a high-volume enumeration burst
# in the same short session, which is the combination Scenario 8 above
# is built around. The 30-day "first time" baseline has to be maintained
# separately (a lookup table updated daily), Sigma alone can't express it.

---
title: MFA Push Fatigue
id: 8f2a1c3e-0000-4000-8000-000000000002
status: experimental
description: >
  Detects an unusually high number of MFA challenges sent to a single
  user in a short window, consistent with an MFA fatigue / push-bombing
  attempt rather than normal sign-in friction.
logsource:
  product: azure
  service: signinlogs
detection:
  mfa_challenge:
    ResultType: '500121'   # MFA denied / not satisfied
  timeframe: 10m
  condition: mfa_challenge | count() by UserPrincipalName > 5
falsepositives:
  - A user genuinely struggling with a flaky authenticator app
  - Shared/service accounts with unusually high legitimate sign-in volume
level: medium
# Reasoning: threshold is deliberately in the "medium" tier rather than
# "high" because the false-positive source (a user just having a bad
# authenticator day) is common enough that this should feed a
# correlation with a subsequent successful sign-in from a new device
# before it becomes a high-priority page, not fire standalone.

---
title: New Administrator Role Granted
id: 8f2a1c3e-0000-4000-8000-000000000003
status: experimental
description: >
  Detects a principal being granted an administrative role in Google
  Workspace, Microsoft 365, or a cloud IAM system.
logsource:
  product: googleworkspace
  service: admin
detection:
  role_grant:
    events.name: 'ASSIGN_ROLE'
    parameters.ROLE_NAME|contains: 'Admin'
  condition: role_grant
falsepositives:
  - Planned, ticketed administrative onboarding (correlate against a
    change-management reference before treating as benign, don't just
    suppress the rule)
level: high
# Reasoning: unlike the other two rules, this one intentionally has NO
# volume or correlation threshold. Admin grants should be rare enough
# that every single one deserves a look; the tuning lever here is a
# change-management lookup for suppression, not a statistical threshold.
```

</CollapsibleCode>

The comments in each rule matter as much as the logic: a Sigma rule without a documented reason for its threshold and a documented false-positive source is exactly the kind of detection that becomes unmaintainable noise six months after whoever wrote it moves to a different team.
