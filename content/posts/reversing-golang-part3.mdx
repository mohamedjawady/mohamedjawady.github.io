> **Series Focus:** Part 1 showed that Go binaries embed PCLNTAB, a table the runtime needs for stack traces, and claimed this means "stripped" Go binaries aren't really stripped. Part 2 reversed concurrency primitives live with GDB, Delve, and Python. This part cashes in Part 1's claim directly: build a symbol-name recovery tool from the real Go runtime source, prove it against ground truth, find out why a well-known production tool fails where it succeeds, and then find the actual boundary of the technique against garble.

## Introduction

Real Go malware ships stripped. `-ldflags="-s -w"` is one flag, it meaningfully shrinks the binary, and it removes every function name `go tool nm` and most disassemblers rely on. A growing minority goes further and runs the binary through [garble](https://github.com/burrowers/garble), which renames every identifier at the source level before compilation and can encrypt string literals too. This isn't a hypothetical: a 2026 DFRWS memory-forensics paper on automated Go malware detection and analysis singles out garble by name as a real obstacle analysts face, noting that it "hashes identifiers and removes metadata to disrupt static analysis" in samples researchers encounter in the wild. Mandiant and Volexity have each shipped dedicated public tooling in the last two years specifically to claw symbols and strings back out of garbled Go malware, GoStringUngarbler and GoResolver respectively, which says plainly how often this comes up in real casework. Both are things an analyst runs into constantly and neither is mysterious once you understand what Go's runtime actually needs to keep working.

Part 1 made a specific, falsifiable claim: Go binaries can't be meaningfully stripped of all useful metadata, because the runtime itself depends on PCLNTAB (the Program Counter Line Table) to produce stack traces during a panic, and that table has to ship in the binary for the language to work correctly. This part tests that claim directly: build a tool that recovers function names from a stripped binary using nothing but the Go runtime's own published struct layout, validate it against known-good output, and then see what happens when the binary fights back.

## The Target

A small program shaped like the kind of thing worth reverse engineering: a license check with a config struct, a fake check-in URL, and a product key.

```go
package main

import (
	"fmt"
	"os"
	"strings"
)

const licenseServer = "https://license.example-vendor.test/v1/check"
const productKey = "TRIAL-7F3A-91C2-XMAS"

type Config struct {
	ServerURL string
	Product   string
	Interval  int
}

func loadConfig() Config {
	return Config{
		ServerURL: licenseServer,
		Product:   productKey,
		Interval:  3600,
	}
}

func checkLicense(cfg Config, key string) bool {
	return strings.EqualFold(key, cfg.Product)
}

func reportStatus(cfg Config, ok bool) string {
	if ok {
		return fmt.Sprintf("checking in with %s every %ds: licensed", cfg.ServerURL, cfg.Interval)
	}
	return fmt.Sprintf("checking in with %s every %ds: unlicensed", cfg.ServerURL, cfg.Interval)
}

func main() {
	if len(os.Args) != 2 {
		fmt.Println("usage: sample <license-key>")
		os.Exit(1)
	}
	cfg := loadConfig()
	ok := checkLicense(cfg, os.Args[1])
	fmt.Println(reportStatus(cfg, ok))
}
```

It never makes a real network call, there's nothing malicious here, it's a stand-in for the shape of a config-and-check-in pattern that shows up constantly in real samples: a URL, a key, a function that validates something, a function that reports status. Built the same debug-friendly way as every binary in this series:

```bash
go build -gcflags="all=-N -l" -o sample.exe main.go
```

```
$ go tool nm sample.exe | grep "main\."
  56bb80 D go:main.inittasks
  4bd8a0 T main.checkLicense
  4bd820 T main.loadConfig
  4bdc40 T main.main
  4bd960 T main.reportStatus
```

Four named functions. This is the ground truth the rest of this post gets checked against.

## Stripping It

```bash
go build -gcflags="all=-N -l" -ldflags="-s -w" -trimpath -o sample_stripped.exe main.go
```

`-s` drops the symbol table, `-w` drops DWARF debug info, `-trimpath` removes local filesystem paths from the binary. The effect is immediate:

```
$ go tool nm sample_stripped.exe
reading sample_stripped.exe: no symbols

$ gdb --batch -ex "break 'main.main'" sample_stripped.exe
No symbol table is loaded.  Use the "file" command.
```

No `go tool nm` output, and GDB can't resolve `main.main` by name anymore. It's also a meaningfully smaller file, 2.25 MB down to 1.5 MB, symbol tables and debug info aren't free. The binary still runs identically:

```
$ ./sample_stripped.exe TRIAL-7F3A-91C2-XMAS
checking in with https://license.example-vendor.test/v1/check every 3600s: licensed
```

And `strings` immediately shows why stripping alone is a weak defense:

```
$ strings sample_stripped.exe | grep -E "license.example-vendor|TRIAL-7F3A"
https://license.example-vendor.test/v1/check
TRIAL-7F3A-91C2-XMAS
```

Stripping removes names. It does nothing to static data. The URL and the key are sitting in plaintext in the file regardless.

## What Survives Stripping: PCLNTAB

Here's the mechanism behind Part 1's claim, read directly from the Go runtime source (`runtime/symtab.go` in the Go 1.23.3 standard library):

```go
type pcHeader struct {
	magic          uint32  // 0xFFFFFFF1
	pad1, pad2     uint8   // 0,0
	minLC          uint8   // min instruction size
	ptrSize        uint8   // size of a ptr in bytes
	nfunc          int     // number of functions in the module
	nfiles         uint    // number of entries in the file tab
	textStart      uintptr // base for function entry PC offsets, equal to moduledata.text
	funcnameOffset uintptr // offset to the funcnametab variable from pcHeader
	cuOffset       uintptr // offset to the cutab variable from pcHeader
	filetabOffset  uintptr // offset to the filetab variable from pcHeader
	pctabOffset    uintptr // offset to the pctab variable from pcHeader
	pclnOffset     uintptr // offset to the pclntab variable from pcHeader
}
```

This struct, 72 bytes on amd64 (an 8-byte prefix plus eight 8-byte offset fields), has to exist somewhere in every Go binary, stripped or not, because `panic()` needs to walk the stack and print function names and line numbers. `-s -w` removes the *separate* symbol table and DWARF sections; it has no reason to touch this structure, since removing it would break `panic` output in production.

Two more pieces complete the picture, both also from `runtime/symtab.go`:

```go
type functab struct {
	entryoff uint32 // relative to runtime.text
	funcoff  uint32
}
```

```go
type _func struct {
	entryOff uint32 // start pc, as offset from moduledata.text/pcHeader.textStart
	nameOff  int32  // function name, as index into moduledata.funcnametab
	// ... (args, pcsp, pcfile, etc.)
}
```

The recovery path is: find the `pcHeader` by its magic number, read `nfunc` entries from the `functab` array, follow each `funcoff` to a `_func` struct, read its `nameOff`, and look that offset up in `funcnametab` to get the actual name string. No debugger, no symbol table, just the file on disk.

## Building the Parser

```python
import struct
import sys
import pefile

MAGIC = b"\xf1\xff\xff\xff"  # go1.16+ pcHeader.magic = 0xfffffff1, little-endian


def read_cstr(data, off):
    end = data.index(b"\x00", off)
    return data[off:end].decode("utf-8", errors="replace")


def parse_pclntab(path):
    pe = pefile.PE(path)
    for s in pe.sections:
        data = s.get_data()
        idx = data.find(MAGIC)
        if idx != -1:
            raw = data
            break
    else:
        raise RuntimeError("pcHeader magic not found")

    hdr = raw[idx: idx + 72]
    magic, pad1, pad2, minLC, ptrSize = struct.unpack_from("<IBBBB", hdr, 0)
    (nfunc, nfiles, textStart, funcnameOff, cuOff, filetabOff,
     pctabOff, pclnOff) = struct.unpack_from("<QQQQQQQQ", hdr, 8)

    funcname_base = idx + funcnameOff
    pcln_base = idx + pclnOff

    funcs = []
    for i in range(nfunc):
        entry_off, func_off = struct.unpack_from("<II", raw, pcln_base + i * 8)
        f = pcln_base + func_off
        fentry_off, name_off = struct.unpack_from("<II", raw, f)
        name = read_cstr(raw, funcname_base + name_off)
        funcs.append((entry_off, name))

    return textStart, funcs
```

This first version assumes `pclntab` lives in `.rdata`, which is where it normally does. Before trusting it against a stripped binary, it has to agree with ground truth on the *unstripped* one:

```
$ python -c "
from pclntab_parse import parse_pclntab
text_start, funcs = parse_pclntab('sample.exe')
for off, name in funcs:
    if name.startswith('main.'):
        print(f'0x{text_start+off:x} {name}')
"
0x4bd820 main.loadConfig
0x4bd8a0 main.checkLicense
0x4bd960 main.reportStatus
0x4bdc40 main.main
```

Every address matches `go tool nm` exactly. Same script, pointed at the stripped binary where `go tool nm` reported nothing:

```
$ python -c "
from pclntab_parse import parse_pclntab
text_start, funcs = parse_pclntab('sample_stripped.exe')
for off, name in funcs:
    if name.startswith('main.'):
        print(f'0x{text_start+off:x} {name}')
"
0x4bd820 main.loadConfig
0x4bd8a0 main.checkLicense
0x4bd960 main.reportStatus
0x4bdc40 main.main
```

Identical addresses. `-s -w` only strips the separately-stored symbol table and DWARF info; the code layout and PCLNTAB are untouched, so the two binaries agree byte for byte on everything this parser reads.

## Where GoReSym Fails, and Why

[GoReSym](https://github.com/mandiant/GoReSym) is Mandiant's production tool for exactly this job, and it's a lot more capable than the 70 lines above: type recovery, build info, multi-format support. It's worth checking against the same stripped binary.

```
$ go install github.com/mandiant/GoReSym@latest
$ GoReSym sample_stripped.exe
{"error": "Failed to parse file: failed to read pclntab: failed to locate pclntab"}
```

It fails, on a binary our own script just handled cleanly. Worth understanding why rather than shrugging and moving on, especially since this exact install resolves fine on every *unstripped* binary in this series:

```
$ GoReSym sample.exe
{
    "Version": "1.23.3",
    "BuildId": "...",
    ...
```

### The Install Command Was the Bug

GoReSym's own source (`objfile/pe.go`) explains part of the gap. Its primary lookup resolves `pclntab` via the PE symbol table (`runtime.pclntab` / `runtime.epclntab`), which `-s` removes, exactly as expected. It does have a fallback byte-scanner for exactly this situation. Checking what `go install ...@latest` actually fetched is worth doing before trusting the diagnosis:

```
$ GoReSym -about 2>&1 | head -1
```

That install pulled **v1.7.1**. A quick check of the project's GitHub releases shows the real latest tag is **v3.4.1**, shipped September 2026, with release notes that specifically call out improved handling of "1.20+ layouts." That's exactly the gap this binary is hitting, and it was apparently already fixed, two major versions ago. Pulling it directly should settle the question:

```
$ go install github.com/mandiant/GoReSym/v3@latest
go: github.com/mandiant/GoReSym/v3@latest: module github.com/mandiant/GoReSym@latest found (v1.7.1), but does not contain package .../v3

$ go install github.com/mandiant/GoReSym/v3@v3.4.1
go: github.com/mandiant/GoReSym/v3@v3.4.1: github.com/mandiant/GoReSym@v3.4.1: invalid version:
module contains a go.mod file, so module path must match major version ("github.com/mandiant/GoReSym/v3")
```

Neither works, and the second error is the real finding: Go's module system requires a module's import path to carry a `/vN` suffix once it passes major version 1 (the [Go Modules Reference](https://go.dev/ref/mod) covers this directly). GoReSym's `go.mod` at the v3.4.1 tag still declares `module github.com/mandiant/GoReSym`, no `/v3`. That's a real packaging bug in the upstream repository, not a caching issue or a mistake in the command above, and it means `go install github.com/mandiant/GoReSym@latest`, the exact command the project's own README recommends, can never resolve past the last v1.x.x-compatible tag. The only way to actually reach v3.4.1 is to clone the tag and build it locally, which sidesteps the module-proxy version check entirely:

```bash
git clone --depth 1 --branch v3.4.1 https://github.com/mandiant/GoReSym.git
cd GoReSym && go build -o GoReSym-v3 .
```

With a binary built from the real latest source:

```
$ ./GoReSym-v3 sample_stripped.exe | python -c "
import json, sys
d = json.load(sys.stdin)
for f in d['UserFunctions']:
    if f['FullName'].startswith('main.'):
        print(hex(f['Start']), f['FullName'])
"
0x4bd820 main.loadConfig
0x4bd8a0 main.checkLicense
0x4bd960 main.reportStatus
0x4bdc40 main.main
```

All four, exact addresses, matching `go tool nm`'s original output and this post's own parser precisely, plus (from the full JSON this post's script doesn't attempt) 107 total recovered functions, type information, and embedded build strings. The underlying data was never the problem. The lesson here is sharper than "update your tools": for a module that violates Go's own major-version-suffix convention, the standard `@latest` install silently caps out below the real latest release with no warning or error, and the only way to know is to check what actually got installed before trusting a negative result.

Checking the current source also answers a narrower question: was the original v1.7.1 gap specific to PE files, or did every format have the same stale list? In v3.4.1, `objfile/elf.go`, `objfile/pe.go`, and `objfile/macho.go` all carry the same four little-endian signatures (`0xFB`, `0xFA`, `0xF0`, and now `0xF1`) plus their big-endian equivalents, consistently across formats. Whatever the state of v1.7.1's ELF path, the fix in the current release wasn't PE-specific.

## Garble: A Different Kind of Opponent

[garble](https://github.com/mvdan.cc/garble) wraps the Go toolchain and rewrites identifiers before compilation, plus (with `-literals`) encrypts string constants so they're only decrypted at the point of use at runtime.

```bash
garble -literals build -o sample_garbled.exe main.go
```

The basics look like stripping, at first:

```
$ go tool nm sample_garbled.exe
reading sample_garbled.exe: no symbols

$ go version -m sample_garbled.exe
sample_garbled.exe: unknown
```

That second line is new. `go version -m` reads a different embedded data structure (Go's module build-info blob, the thing `govulncheck` relies on) that survives plain `-s -w` stripping untouched, Part 1 and the sections above never had to think about it. Garble strips it specifically; it's a separate, deliberate design decision from symbol stripping. And `-literals` does what it claims:

```
$ strings sample_garbled.exe | grep -E "license.example-vendor|TRIAL-7F3A"
$ echo $?
1
```

Nothing. No plaintext URL, no plaintext key anywhere in the file. That's a real improvement over plain stripping, where both were sitting in cleartext.

### When the Parser Hits Its Actual Limit

Pointing the same PCLNTAB parser at the garbled binary:

```
$ python -c "from pclntab_parse import parse_pclntab; parse_pclntab('sample_garbled.exe')"
Traceback (most recent call last):
  ...
RuntimeError: pcHeader magic not found in any section
```

It fails, honestly, not silently. Scanning every section (not just `.rdata`, since by this point it's worth checking whether garble moved things around) and validating every candidate (`pad1`/`pad2` must be zero, `ptrSize` must be 4 or 8) turns up nothing that passes. The accounting, checked carefully rather than eyeballed: 45 raw 4-byte matches of the magic sequence in `.text`, all coincidental code bytes (one, for instance, is immediately followed by `5d c3`, `pop rbp; ret`, ordinary instructions, not a header), and 2 matches in `.data` that fail validation outright (`ptrSize=0`). Nothing in `.rdata`, `.pdata`, or anywhere else carries a valid header. An earlier pass at this investigation mis-mapped a file offset into `.pdata`'s address range and reported a false hit there; rechecking it with the same per-section extraction the actual script uses shows that was a bookkeeping error, not a real location, worth stating plainly since the whole point of this series is capturing what tools actually say rather than what seems plausible. The genuine header, wherever it ends up, simply doesn't carry an intact `0xfffffff1` signature the way the stripped-only binary's did.

This time it's worth checking against the real GoReSym v3.4.1, built from source, not the stale v1.7.1 the naive install command returns:

```
$ ./GoReSym-v3 sample_garbled.exe
DEBUG: validateAndConvertModuleData_116 minpc validation failed: 94c000000000 != 140001000
DEBUG: validateAndConvertModuleData_116 minpc validation failed: 94c000000000 != 140001000
DEBUG: validateAndConvertModuleData_116 minpc validation failed: 94c000000000 != 140001000
{"error": "Failed to parse file: no valid pclntab found"}
```

Still fails, but visibly differently than v1.7.1 did. The current version has more heuristics than a flat magic scan, it's actually locating candidate `moduledata` structures and cross-validating them against the binary's real text-section address, and every candidate it finds fails that cross-check. That's a stronger, more specific failure than "couldn't find the header at all," and it's better evidence that garble's obfuscation is deliberately targeting this exact class of recovery, not just outrunning one tool's stale signature list. The current, actively maintained, version-complete release of the field's standard tool hits the same wall this post's own parser did.

### Testing the Purpose-Built Tool

[GoStringUngarbler](https://github.com/mandiant/gostringungarbler) exists for exactly the gap `-literals` opens: Mandiant built it specifically to decrypt garble's string obfuscation. Worth testing against the actual target rather than assuming it would work:

```
$ python GoStringUngarbler -i sample_garbled.exe -o out_decrypted.exe -s strings_dump.txt
INFO:root:Stack obfuscated string count: 0 strings.
INFO:root:Split obfuscated string count: 0 strings.
INFO:root:Seed obfuscated string count: 0 strings.
INFO:root:Done generating patches for 0 functions.
```

`strings_dump.txt` comes out empty. Not an error, a clean run that recovers nothing. The tool's own documentation states its supported range plainly: garble v0.11.0 through v0.13.0, Go 1.21 through 1.23. This post's garbled binary was built with garble v0.18.0 on Go 1.27.2, outside that window on both axes, because garble's internal obfuscation scheme changes between releases the same way Go's pcHeader magic changed between runtime versions. It's the identical lesson as the GoReSym detour above, landing on a second, independent, purpose-built tool: version drift between a fast-moving obfuscator and the tooling built to reverse it is the normal state of things here, not an edge case. [GoResolver](https://github.com/volexity/goresolver), Volexity's control-flow-graph-based alternative for resolving garbled symbols, is a different approach to the same problem and worth knowing about even though this post didn't get it running in this environment.

## Where Static Analysis Hands Off to Live Analysis

Static recovery has a real limit against garble, backed now by three independent tools hitting it. But the binary still has to run correctly, obfuscation happens in the file on disk, not in what the program does at runtime. Part 2 of this series built real competence with GDB and Delve; the obvious next question is whether that competence survives contact with a garbled target.

The honest answer is: only partially. Delve attaches and runs the binary without complaint, but the thing that made Delve worth installing in Part 2, native goroutine awareness, depends on locating the same runtime type and symbol metadata garble is built to remove:

```
$ dlv exec ./sample_garbled.exe --check-go-version=false -- TRIAL-7F3A-91C2-XMAS
(dlv) goroutines
Command failed: could not find goroutine array
checking in with https://license.example-vendor.test/v1/check every 3600s: licensed
```

The program runs to completion correctly. Delve's structured introspection, the exact capability that gave Part 2 its edge over plain GDB, fails for the same underlying reason the static tools above do: garble's metadata stripping doesn't discriminate between "what a disassembler needs" and "what a debugger needs," it removes the type and symbol information both depend on. A live debugger attached to a garbled process is not automatically more capable than a static one; it inherits the same blind spot unless you're willing to work entirely in raw addresses and registers, with no symbolic help from the debugger at all.

What *does* survive, with zero extra tooling, is simply running the program and reading its output:

```
$ ./sample_garbled.exe TRIAL-7F3A-91C2-XMAS
checking in with https://license.example-vendor.test/v1/check every 3600s: licensed
```

Same real URL, same real key, printed in plain text to stdout, from a binary where neither string exists anywhere in the file and no tool tested in this post, static or dynamic, purpose-built or hand-rolled, could locate them at rest. Whatever garble did to the static data, the program has to reconstruct the real values in memory before it can use them, and that reconstruction is observable through the most basic interaction possible: run it, watch what it does. That's the actual, now-verified boundary: structured recovery, whether reading the file or attaching a symbol-aware debugger, stops at the same wall garble is built to put up; unstructured observation of real behavior does not, because it was never the kind of recovery garble defends against in the first place.

## Side by Side

| | Unstripped | Stripped (`-s -w`) | Garbled (`-literals`) |
|---|---|---|---|
| `go tool nm` | Full symbol list | `no symbols` | `no symbols` |
| `go version -m` | Works | Works | `unknown` |
| Hand-rolled PCLNTAB parser | 4/4 functions | 4/4 functions | Fails, validated no match |
| GoReSym v1.7.1 (`@latest`) | Works | Fails (stale magic list) | Fails |
| GoReSym v3.4.1 (built from source) | Works | 4/4 functions + types, strings | Fails (candidates found, all invalid) |
| GoStringUngarbler | N/A (nothing encrypted) | N/A | 0 strings recovered (version mismatch) |
| `strings` on URL/key | Plaintext | Plaintext | Nothing |
| `dlv goroutines` | Full goroutine list | Full goroutine list | `could not find goroutine array` |
| Running it and reading stdout | Real values | Real values | **Real values** |

Every row that depends on symbol or type metadata fails the same way against garble, regardless of whether the tool reads the file or attaches a debugger. Only the last row, which depends on nothing but the program executing, survives all three builds unchanged.

## Conclusion

Five claims, tested against real binaries and real tools instead of assumed:

1. **"Stripped Go binaries aren't really stripped" is true, specifically and narrowly.** `-s -w` removes the symbol table and DWARF info. It does not and structurally cannot remove PCLNTAB without breaking `panic`, which is why a 70-line parser built from the published runtime struct layout recovers every function name a debug build has, verified address-for-address against `go tool nm` ground truth.
2. **Check what a tool actually installed before trusting what it says.** GoReSym's naive `go install ...@latest` silently returns a build two major versions behind the real latest, because the upstream repository's `go.mod` doesn't follow Go's own major-version-suffix convention. The real v3.4.1 recovers everything the stripped binary has; the stale v1.7.1 everyone's `@latest` actually installs cannot. The failure was in the install command, not in the data.
3. **Garble moves the goalposts, for real, against every tool this post tried.** A hand-rolled parser, GoReSym's current release with its richer validation heuristics, and Mandiant's own purpose-built string decryptor all fail against this binary, independently, for related but distinct reasons.
4. **Dynamic analysis isn't automatically immune.** Delve's goroutine-aware superiority, the whole case for installing it in Part 2, depends on the same metadata garble strips. Attaching a debugger to a garbled process doesn't bypass the obfuscation; it runs into the identical wall from a different direction.
5. **The one thing that can't be obfuscated away is the program actually running.** Every tool above fails by trying to recover something *at rest*, in a file or in structured runtime metadata. Running the binary and reading what it does bypasses the entire category, not because it's a cleverer technique, but because it was never playing the game garble is built to defend.
