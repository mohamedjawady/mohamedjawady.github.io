> **Blue Team Focus:** Visibility is not a product you buy, it's a property of where you decided to look. This post maps the actual collection points across a modern environment, then walks six real attack shapes through them to show exactly where each one lights up, and where it doesn't.

**TL;DR:** Every collection point sees a specific slice of an attack and is structurally blind to the rest, network sensors see the wire and not the process, endpoint sensors see the process and not what's already inside an established session, identity logs see authentication and not what happens after. No single layer is a visibility strategy by itself. The six scenarios below, three identity-and-cloud, three web application, all make the same point from a different angle: the collection point that would have actually caught the attack is very often the one nobody turned on, not the one nobody bought.

## Introduction

Ask most security teams whether they have visibility and the answer is almost always yes, in the sense that a dashboard somewhere is green. Ask them whether they'd have caught a specific attack chain and the answer gets a lot less certain, because "visibility" as a checkbox and visibility as "the specific telemetry that would have shown this specific behavior" are different claims, and the gap between them is where most real intrusions actually live.

This post is a map, not a product review. It covers where defensive telemetry actually gets generated across a typical enterprise, organized by the layer that generates it, what each layer structurally can and cannot see, and then six scenarios, three built around identity and cloud infrastructure, three built around web application attacks, that make the abstract argument concrete: here is exactly which collection point lit up, and here is exactly which one stayed dark and why.

## The Collection Point Taxonomy

Five layers generate the overwhelming majority of defensive telemetry in a modern environment. None of them is optional, and none of them is sufficient alone.

### Network

Network telemetry sees what crosses the wire: NetFlow and full packet capture for traffic patterns and payloads, DNS logs for resolution requests, proxy and firewall logs for what left the perimeter and where it went. This is the layer covered in depth by the Network Architecture and Security Onion posts on this blog, and it remains the only layer that reliably sees lateral movement between two hosts neither of which has an agent installed, a gap that shows up constantly in segmented or legacy environments.

What it structurally cannot see: anything inside encrypted traffic without TLS interception, and nothing at all about what a process is actually doing on a host, only that the host talked to something.

| Source | What it sees | What it can't | Retention reality |
|---|---|---|---|
| NetFlow | Connection metadata: who talked to whom, when, how much | Payload content | Often kept for months, it's cheap |
| Full packet capture | Payload content, protocol detail | Encrypted payloads without inspection; storage cost limits retention | Frequently days, sometimes hours |
| DNS logs | Every resolution request, a proxy for "what did this host try to reach" | Traffic that skips DNS (direct IP, DNS-over-HTTPS to an uncontrolled resolver) | Usually good, DNS logs are cheap to keep |
| Proxy / firewall logs | Perimeter crossings, URL categories, blocked/allowed decisions | East-west traffic that never crosses the perimeter | Varies widely by vendor |

### Endpoint

Endpoint telemetry sees what a process does: EDR agents, <Term concept="sysmon">Sysmon</Term>, native OS auditing, and Attack Surface Reduction rules, covered for the Windows-specific case in Part 7 of the Active Directory series. This is the only layer that reliably sees process ancestry, command-line arguments, and in-memory behavior like LSASS access.

What it structurally cannot see: anything that happens before an agent is installed or after it's been disabled or evaded, and by definition nothing on a host the organization doesn't own, which matters more than it sounds once SaaS and BYOD are involved.

### Identity

Identity telemetry sees authentication and authorization decisions: domain controller security logs (event 4768/4769/4624 and the rest, covered throughout the AD series and in the dedicated Kerberos/NTLM post), Entra sign-in logs, and Conditional Access evaluation logs. This is the layer that catches Kerberoasting, AS-REP Roasting, and DCSync, all covered in Part 3 of the AD series, often before any endpoint or network signal exists at all, because the abuse is entirely a protocol-level request that never touches a process the way a normal attack does.

What it structurally cannot see: anything that happens after a session is already established. A successful authentication event says someone got in; it says nothing about what they did once they were inside, which is exactly why identity logs alone are never the whole picture even for identity-centric attacks.

### Cloud / SaaS

Cloud and SaaS telemetry, API audit logs (the AWS CloudTrail/Azure Activity Log shape), SaaS platform activity logs, and OAuth grant history, is the newest of the five layers and the one most environments underinvest in relative to how much of the actual attack surface now lives there. It's also structurally separate from on-prem identity and endpoint visibility: a compromised OAuth token or a malicious third-party app grant can operate entirely within a SaaS platform's own API surface and never generate a single on-prem log line, which is exactly Scenario 3 below.

### Email

Email telemetry, gateway logs, message headers, and attachment detonation sandboxes, sees the initial access vector for most intrusions that don't start with an exposed application. It answers "did this org receive the lure" and "what did the attachment actually do when detonated," which is a narrower but still essential question than any of the other four layers ask.

## The Blind Spot Principle

The pattern across all five layers is the same one, stated once so the scenarios below don't have to repeat it: **every collection point's blind spot is shaped by where it physically or logically sits relative to the attack.** A sensor on the wire cannot see inside a process. A sensor on a process cannot see what already happened inside an encrypted session it wasn't running during. A log of authentication decisions cannot describe behavior after the decision was made. This isn't a maturity problem that better tooling eventually solves, it's a structural property of what each collection point was built to observe, and it is exactly why "we have an EDR" or "we have a SIEM" answers a much smaller question than most people asking it think it does.

## Six Scenarios

Each scenario below is short by design, the underlying techniques already have full treatments elsewhere on this blog. The point here is narrower and more specific: which collection point actually produced the signal, and which one a defender might reasonably have assumed would, but didn't.

### Scenario 1: Kerberoasting, Caught by One Layer, If It's Configured

Covered in full in [Part 3 of the Active Directory series](/posts/active-directory-security-part3). An attacker with any valid domain credential requests a Kerberos service ticket for an account with a registered SPN and cracks it offline. No malware runs. No network connection leaves the environment. No endpoint agent has anything to alert on, because nothing happened on any endpoint, the whole attack is a single, protocol-legitimate request to a domain controller.

### Scenario 2: Coercion Relayed to RBCD, No Single Layer Sees the Whole Chain

Covered in full ("RBCD Without the ACE") in [Part 3 of the Active Directory series](/posts/active-directory-security-part3). An attacker coerces a machine into authenticating outward, relays that authentication to LDAP, writes a delegation attribute, then runs an S4U2Self/S4U2Proxy chain to impersonate a privileged user. This one is deliberately the middle scenario in this post because it's the clearest counterexample to "just watch the identity layer": the chain touches three different layers, and each one sees a different, incomplete piece.

### Scenario 3: OAuth Token Theft, Invisible On-Prem by Design

A phishing page tricks a user into approving a malicious OAuth application's request for mailbox and file access scopes against their Microsoft 365 or Google Workspace account. From that point forward, the attacker authenticates using the token that grant produced, directly against the SaaS platform's own API. No domain controller is ever contacted. No endpoint agent sees anything, since the entire session happens between the attacker's own infrastructure and the SaaS provider's API, with the victim's device not even involved after the initial click.

### Scenario 4: SQL Injection, the Collection Point That Proves It Is Usually Off

An attacker submits a crafted input to a web form, extracting data through a classic SQL injection against the backend database. The <Term concept="waf">WAF</Term> or application log, if either exists, typically records that a request matching an injection pattern arrived and was blocked or allowed, a useful but shallow signal: it says "something suspicious happened here," not what the resulting query actually returned. The record that would actually prove impact, the database's own query or audit log showing the exact statement executed and what it returned, is disabled by default in most database engines specifically because full query logging carries a real performance cost at scale.

### Scenario 5: SSTI, the Request and the Damage Are in Different Layers

Server-Side Template Injection happens when user input gets evaluated by a server-side templating engine instead of just being inserted into it, and on a vulnerable engine that evaluation can escalate all the way to arbitrary code execution. What makes this scenario worth including specifically: the request that triggers it looks, at the application and WAF layer, like an unusually formatted but otherwise ordinary web request. The actual damage, a spawned process, a written file, an outbound connection initiated by the web server process itself, shows up entirely at the endpoint layer, on a host most web-layer monitoring was never watching in the first place.

### Scenario 6: SSRF, Where the Only Real Witness Is the Metadata Endpoint

Server-Side Request Forgery tricks a server into making a request on the attacker's behalf, most valuably toward internal-only targets the attacker couldn't otherwise reach, including a cloud provider's instance metadata service, which on both AWS and Azure by default answers unauthenticated requests from the instance itself with the credentials that instance's role is allowed to use. At the network layer, this outbound request from the application server looks identical to any other outbound request the application makes constantly; nothing about its shape flags it as abnormal.

## Building a Coverage Map

Six scenarios are illustrations, not an inventory. The actual exercise worth running is systematic: take the techniques most relevant to your environment, ideally sourced from MITRE ATT&CK's own data source mappings, and for each one, mark which of the five layers above would actually produce a signal, whether that source is currently collected at all, and whether it's retained long enough to matter by the time an investigation needs it.

<CollapsibleCode title="Collection Coverage Map Template" language="markdown">

```markdown
TECHNIQUE: [name, ATT&CK ID if applicable]

| Layer | Would produce a signal? | Currently collected? | Retention |
|---|---|---|---|
| Network | Yes/No/Partial | Yes/No | [duration] |
| Endpoint | Yes/No/Partial | Yes/No | [duration] |
| Identity | Yes/No/Partial | Yes/No | [duration] |
| Cloud/SaaS | Yes/No/Partial | Yes/No | [duration] |
| Email | Yes/No/Partial | Yes/No | [duration] |

GAP: [which "Yes" rows are actually "No" in practice]
COST TO CLOSE: [what turning this on requires: license, storage, engineering time]
PRIORITY: [is this technique likely enough against this environment to justify it]
```

</CollapsibleCode>

This is the same discipline the Collection Management Framework post on this blog covers in depth for an intelligence program specifically, sources, coverage, gaps, and a documented price tag for closing each one. The version here is the same idea applied one layer down: not "what can our intelligence program answer," but "what would our own logs actually show if this exact technique happened tomorrow."

## Conclusion

None of the six scenarios above involved a novel technique. Every one of them is well documented, several are covered in full elsewhere on this blog, and none require a defender to predict something nobody has seen before. What they require is knowing, in advance and specifically, which collection point was ever going to see which step, because by the time an incident is underway is the most expensive possible moment to discover that the layer that would have caught it was never turned on. Visibility isn't a line item. It's a map, and the map is only useful if someone actually checked where the lines don't reach.
